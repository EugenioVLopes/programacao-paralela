Lição 03: Paralelismo ao Nível de Instrução (ILP) e Otimização

Tarefa 03 • Dissecção de tarefa03.c • Dependências de dados, múltiplos acumuladores, níveis de otimização e quizzes simétricos

1. Contexto e ponto de partida

Base teórica na Teoria 03

Poder computacional, Power Wall e o papel do ILP estão em Fundamentação teórica. Abaixo: dissecção de tarefa03.c e medição por nível de otimização.

Operações de redução vetorial (como somar todos os elementos de um vetor com centenas de milhões de números) constituem a base computacional de inúmeras aplicações de alto impacto:

  • Treinamento de Redes Neurais e LLMs: o cálculo de funções de perda (como Cross-Entropy), regularização $L_2$ e normalizações de camadas (LayerNorm, RMSNorm) dependem de reduções contínuas sobre tensores de bilhões de parâmetros.
  • Simulações Numéricas e Métodos Iterativos: algoritmos de álgebra linear (como Gradiente Conjugado) avaliam produtos escalares $\mathbf{x}^T \mathbf{y}$ repetidamente a cada iteração para resolver sistemas de equações com milhões de variáveis.
  • Física Computacional e Astrofísica: integração numérica de grandezas conservadas (energia total, momento linear e angular) em problemas de $N$-corpos.
  • Processamento de Dados e Estatística em Tempo Real: computação de médias, variâncias e correlações em fluxos massivos de telemetria e sinais de radares.

Somar $10^8$ elementos em um único processador parece uma tarefa trivial ($O(N)$), mas a forma como as instruções são estruturadas pode fazer o código executar até 6 vezes mais rápido sem alterar o hardware.

2. Dissecção linha a linha de tarefa03.c

1. Macros e cabeçalhos de sistema

#define _POSIX_C_SOURCE 199309L

#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define DEFAULT_N 100000000L
  • #define _POSIX_C_SOURCE 199309L: macro de conformidade POSIX que expõe clock_gettime e a constante CLOCK_MONOTONIC no cabeçalho <time.h>. Deve preceder todos os #include.
  • DEFAULT_N 100000000L: define o tamanho padrão do vetor ($10^8$ elementos, ~400 MB de memória para inteiros de 32 bits). O sufixo L garante tipo long.

2. Função de temporização em nanossegundos

static double agora(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}
  • struct timespec: armazena segundos (tv_sec) e nanossegundos (tv_nsec).
  • CLOCK_MONOTONIC: relógio estritamente crescente que mede tempo de parede real, imune a ajustes de horário via NTP.
  • return t.tv_sec + t.tv_nsec / 1e9: converte o timestamp completo para segundos em ponto flutuante de precisão dupla (double).

3. Leitura de parâmetros e alocação dinâmica

long n = argc > 1 ? atol(argv[1]) : DEFAULT_N;
if (n <= 0) {
    fprintf(stderr, "Uso: %s [numero_de_elementos]\n", argv[0]);
    return 1;
}

int *v = malloc((size_t)n * sizeof(*v));
if (!v) {
    perror("malloc");
    return 1;
}
  • atol(argv[1]): converte a string do argumento para long, permitindo testar diferentes ordens de grandeza pela linha de comando.
  • malloc((size_t)n * sizeof(*v)): aloca $10^8 \times 4\text{ bytes} \approx 381{,}47\text{ MB}$ na heap. O cast (size_t) previne overflow aritmético no cálculo de bytes.
  • if (!v): checagem defensiva obrigatória contra falhas de alocação de memória do sistema operacional.

4. Laço de inicialização

double inicio = agora();
for (long i = 0; i < n; ++i)
    v[i] = (int)(3 * i + 1);
double tempo_inicializacao = agora() - inicio;
  • Cada iteração escreve em um índice independente v[i]. Não há dependências de dados entre iterações distintas ($i$ e $i+1$).
  • O compilador consegue vetorizar este laço facilmente usando instruções SIMD ou desenrolá-lo sem restrições.
  • Além do cálculo, este laço força os page faults de primeira escrita no Linux, alocando páginas físicas na memória DRAM.

5. Laço de soma dependente (acumulador único)

inicio = agora();
long long soma_dependente = 0;
for (long i = 0; i < n; ++i)
    soma_dependente += v[i];
double tempo_dependente = agora() - inicio;
  • long long (64 bits): evita overflow, pois a soma de $10^8$ elementos atinge $\approx 1{,}5 \times 10^{16}$, ultrapassando o limite de 32 bits ($\approx 2 \times 10^9$).
  • Dependência RAW (Read-After-Write): a adição da iteração $i+1$ precisa ler soma_dependente que acabou de ser calculada na iteração $i$.
  • Cria um caminho crítico sequencial de $N$ instruções encadeadas. A CPU é forçada a esperar a latência de cada adição terminar antes de iniciar a próxima.
Gargalo do acumulador único

Mesmo que a CPU tenha 4 unidades aritméticas capazes de somar em paralelo, apenas 1 unidade é utilizada porque as operações não possuem operandos prontos ao mesmo tempo.

6. Laço com múltiplos acumuladores (4 cadeias independentes)

inicio = agora();
long long s0 = 0, s1 = 0, s2 = 0, s3 = 0;
long i = 0;
for (; i + 3 < n; i += 4) {
    s0 += v[i];
    s1 += v[i + 1];
    s2 += v[i + 2];
    s3 += v[i + 3];
}
for (; i < n; ++i)
    s0 += v[i];
long long soma_multiplos = s0 + s1 + s2 + s3;
double tempo_multiplos = agora() - inicio;
  • s0, s1, s2, s3: quatro registradores acumuladores independentes.
  • No corpo do laço, as quatro adições são mutuamente independentes: s0 depende apenas do valor anterior de s0, s1 apenas de s1, etc.
  • O processador superescalar pode despachar as quatro somas no mesmo ciclo de clock, ocupando múltiplas portas de execução simultaneamente.
  • for (; i < n; ++i) s0 += v[i];: tail loop (laço de cauda) que soma os elementos remanescentes caso $N$ não seja múltiplo exato de 4.
  • s0 + s1 + s2 + s3: redução final das somas parciais em um único valor escalar.

7. Impressão, liberação de memória e validação

printf("N=%ld inicializacao=%.9f dependente=%.9f multiplos=%.9f "
       "somas=%lld,%lld\n", n, tempo_inicializacao,
       tempo_dependente, tempo_multiplos, soma_dependente,
       soma_multiplos);
free(v);
return soma_dependente != soma_multiplos;
  • Imprime os tempos com 9 casas decimais (resolução de nanossegundos).
  • free(v): desaloca o bloco de 400 MB da heap.
  • return soma_dependente != soma_multiplos: código de saída retorna 0 (sucesso) se ambas as somas forem idênticas ou 1 caso haja discrepância numérica.

3. Análise de desempenho por nível de otimização (-O0, -O2, -O3)

Abaixo estão os dados empíricos medidos no ambiente de teste para $N = 100.000.000$ inteiros:

Nível Inicialização (s) Soma dependente (s) Múltiplos acumuladores (s) Speedup relativo
-O0 (sem otimização) 0,30058 s 0,15114 s 0,05847 s 2,58× mais rápido
-O2 (otimização padrão) 0,10249 s 0,02825 s 0,02616 s 1,08× mais rápido
-O3 (otimização agressiva) 0,10935 s 0,02617 s 0,03044 s 0,86× (efeito SIMD)

Interpretação dos fenômenos observados

  1. Em -O0 (2,58× de speedup): o compilador gera código direto para a pilha sem registrar variáveis. A versão com 4 acumuladores quebra a cadeia de dependências e permite que a unidade de execução fora de ordem (OoO) do processador execute múltiplas instruções por ciclo.
  2. Em -O2 (ganho de ~5,8× sobre O0): o compilador aloca acumuladores diretamente em registradores e aplica desenrolamento automático de laços. O gargalo passa a ser a largura de banda de leitura da memória.
  3. Em -O3 (vetorização automática SIMD): o GCC vetoriza o laço de acumulador único gerando instruções vetoriais (AVX2/SSE) que acumulam múltiplos dados por instrução. Isso torna a versão de acumulador único tão rápida quanto (ou ligeiramente mais rápida que) a versão manual de 4 acumuladores.

4. Quizzes interativos

Questão 1 de 4
Por que o laço com um único acumulador (soma += v[i]) não consegue utilizar todas as portas de execução aritmética disponíveis no núcleo do processador?
Correto! Existe uma dependência verdadeira de dados do tipo RAW (Read-After-Write). Cada adição depende do resultado da adição anterior, formando uma cadeia crítica que força o processador a executar uma soma após a outra sequencialmente, sem explorar o pipeline superescalar.
Questão 2 de 4
Qual mecanismo de microarquitetura explica o speedup de 2,6× obtido ao usar quatro acumuladores independentes (s0, s1, s2, s3) em nível -O0?
Correto! Com quatro acumuladores independentes, quebra-se a dependência estrita entre adições adjacentes. A unidade superescalar pode disparar até 4 instruções de soma por ciclo, aproveitando as múltiplas ALUs do mesmo núcleo (ILP — Paralelismo ao Nível de Instrução).
Questão 3 de 4
Por que a vantagem percentual da versão manual com múltiplos acumuladores praticamente desaparece quando compilamos com os níveis de otimização -O2 e -O3?
Correto! Compiladores modernos com -O3 aplicam vetorização automática (SIMD) e desenrolamento de laço com acumuladores vetoriais ocultos, realizando o mesmo trabalho que a técnica manual e saturando a largura de banda da memória.
Questão 4 de 4
Por que a função clock_gettime(CLOCK_MONOTONIC) é a escolha recomendada para medir o tempo de execução em experimentos de computação de alto desempenho?
Correto! O relógio monotônico garante contagem contínua e imutável do tempo de parede (wall time) com resolução de nanossegundos ($10^{-9}$ s), essencial para benchmarks de alta precisão e algoritmos paralelos.

1. Pipeline: a linha de montagem do processador

Um processador sequencial ingênuo executaria cada instrução completamente antes de iniciar a próxima. A técnica de pipeline divide a execução em estágios (tipicamente 5 a 20+), cada um responsável por uma fase: busca (fetch), decodificação (decode), execução (execute), acesso à memória (memory) e escrita (writeback).

Com o pipeline, múltiplas instruções ocupam estágios diferentes simultaneamente — como uma linha de montagem industrial. Um pipeline de $k$ estágios pode ter até $k$ instruções em voo ao mesmo tempo.

$$\text{Throughput}_{\text{ideal}} = 1 \text{ instrução/ciclo} \quad (\text{pipeline de } k \text{ estágios totalmente preenchido})$$

O pipeline não reduz a latência de uma instrução individual — cada uma ainda leva $k$ ciclos do início ao fim. O ganho está no throughput: uma nova instrução pode ser iniciada a cada ciclo.

Hazards: quando o pipeline para

Três tipos de situação podem forçar o pipeline a inserir "bolhas" (ciclos de espera):

  • Hazard estrutural: dois estágios competem pelo mesmo recurso de hardware (ex.: uma única porta de memória compartilhada entre busca e acesso a dados).
  • Hazard de dados: uma instrução depende do resultado de outra que ainda não terminou (principal foco desta tarefa).
  • Hazard de controle: um desvio condicional (if, for) pode invalidar instruções já buscadas, exigindo flush do pipeline.

2. Execução superescalar e janela de instrução

Processadores modernos são superescalares: contêm múltiplas unidades de execução e podem iniciar 4 a 6 instruções por ciclo (ou mais). Um Intel Skylake, por exemplo, possui 4 portas de execução aritmética inteira e 2 unidades de ponto flutuante (FMA).

Para alimentar essas unidades, o processador mantém uma janela de instrução (instruction window ou ROB — Reorder Buffer) com 200 a 500+ instruções em análise simultânea. O hardware examina essa janela buscando instruções independentes que possam executar em paralelo.

Capacidade superescalar — números reais
Microarquitetura Despacho máximo ROB (entradas) Portas de FP
Intel Skylake (2015) 6 µops/ciclo 224 2 (FMA de 256 bits)
Intel Golden Cove (2021) 6 µops/ciclo 512 2 (FMA de 256 bits)
AMD Zen 4 (2022) 6 µops/ciclo 320 2 (FMA de 256 bits)

O ILP (Instruction-Level Parallelism) é a quantidade de paralelismo disponível dentro de um fluxo sequencial de instruções. A capacidade superescalar existe para explorar ILP — mas só funciona quando há instruções independentes suficientes na janela.

3. Dependências de dados: RAW, WAR e WAW

A classificação formal de dependências usa a terminologia de Bernstein (1966):

Tipo Sigla Descrição Eliminável por hardware?
Dependência verdadeira RAW (Read After Write) Instrução B lê resultado que A produz Não — é física
Antidependência WAR (Write After Read) B escreve em registrador que A ainda lê Sim — renomeação
Dependência de saída WAW (Write After Write) A e B escrevem no mesmo registrador Sim — renomeação

Na Tarefa 03, o laço com acumulador único contém uma cadeia RAW inevitável: 

// Cada iteração depende do resultado da anterior:
//   soma += v[i]   →   soma = soma_anterior + v[i]
//   RAW: a soma da iteração i+1 precisa do valor produzido na iteração i
for (long i = 0; i < n; ++i)
    soma_dependente += v[i];  // cadeia de N somas encadeadas

Essa cadeia de $N$ adições sequenciais forma o caminho crítico do laço. O hardware não pode começar a soma da iteração $i+1$ antes de obter o resultado de $i$, independentemente de quantas unidades funcionais estejam disponíveis.

4. Execução fora de ordem e renomeação de registradores

Processadores x86 modernos implementam execução fora de ordem (Out-of-Order Execution, OoOE). O front-end decodifica instruções em ordem, mas o back-end pode executá-las em qualquer sequência, desde que as dependências RAW sejam respeitadas.

A renomeação de registradores elimina falsas dependências WAR e WAW. O processador mantém centenas de registradores físicos internos (muito mais que os 16 registradores arquiteturais x86_64) e mapeia cada escrita para um registrador físico diferente. Assim, instruções que escrevem no mesmo registrador lógico podem executar em paralelo.

Consequência para o laço de acumulador único

A renomeação de registradores não ajuda com a cadeia RAW do acumulador único: a adição soma += v[i] tem dependência verdadeira — o resultado da iteração $i$ é dado de entrada da iteração $i+1$. Nenhum truque de hardware elimina isso. A única solução é reestruturar o código para criar cadeias independentes.

5. Caminho crítico e latência de operações

Cada operação aritmética tem dois tempos: latência (ciclos até o resultado estar pronto) e throughput recíproco (ciclos mínimos entre inícios de operações independentes na mesma unidade).

Operação Latência (ciclos) Throughput recíproco Exemplo (Intel Skylake)
ADD inteiro 1 0,25 ciclo (4 por ciclo) add rax, rbx
ADDSD (FP double) 4 0,5 ciclo (2 por ciclo) addsd xmm0, xmm1
MULSD (FP double) 4 0,5 ciclo (2 por ciclo) mulsd xmm0, xmm1
VFMADD (FP FMA) 4 0,5 ciclo (2 por ciclo) vfmadd231sd xmm0, xmm1, xmm2

Acumulador único: limitado pela latência

No laço soma += v[i], a adição inteira tem latência de 1 ciclo. O resultado de cada iteração alimenta a próxima, então o laço executa a 1 adição por ciclo, apesar de o hardware poder fazer 4 adições independentes por ciclo. Apenas 25% da capacidade é utilizada.

$$T_{\text{dependente}} = N \times L_{\text{add}} = N \times 1 \text{ ciclo}$$

Quatro acumuladores: limitado pelo throughput

Com 4 acumuladores independentes (s0, s1, s2, s3), o processador pode iniciar até 4 adições por ciclo (uma em cada porta). O tempo total cai para aproximadamente:

$$T_{\text{múltiplos}} \approx \frac{N}{4} \times \frac{1}{\text{throughput}} = \frac{N}{4} \times 0{,}25 = \frac{N}{16} \text{ ciclos (ideal)}$$

Na prática, a melhoria é limitada pela largura de banda de memória (leitura de v[i]) e pelo custo da redução final s0 + s1 + s2 + s3. O speedup observado na Tarefa 03 (2,6× em -O0) é coerente com a remoção parcial do gargalo de latência.

6. Desenrolamento de laços e múltiplos acumuladores

O loop unrolling é a técnica de replicar o corpo de um laço $k$ vezes dentro de uma única iteração, reduzindo o overhead de controle (branch, incremento) e criando mais instruções independentes na janela de execução.

O desenrolamento por si só não é suficiente para quebrar a cadeia de dependência. Se o laço desenrolado usa o mesmo acumulador, a cadeia RAW permanece: 

/* Desenrolado SEM múltiplos acumuladores: NÃO remove a dependência */
for (; i + 3 < n; i += 4) {
    soma += v[i];      // depende de soma anterior
    soma += v[i + 1];  // depende da linha acima
    soma += v[i + 2];  // depende da linha acima
    soma += v[i + 3];  // depende da linha acima
}

O truque decisivo é combinar desenrolamento com acumuladores separados. Cada cadeia de somas é independente das demais: 

/* Desenrolado COM múltiplos acumuladores: 4 cadeias independentes */
for (; i + 3 < n; i += 4) {
    s0 += v[i];      // cadeia s0: s0 depende só do s0 anterior
    s1 += v[i + 1];  // cadeia s1: independente de s0
    s2 += v[i + 2];  // cadeia s2: independente de s0, s1
    s3 += v[i + 3];  // cadeia s3: independente de s0, s1, s2
}
Número ideal de acumuladores

O número ótimo de acumuladores depende da razão $\frac{\text{latência}}{\text{throughput recíproco}}$. Para adição inteira no Skylake: latência = 1, throughput recíproco = 0,25 → razão = 4. Para FP: latência = 4, throughput recíproco = 0,5 → razão = 8. Usar mais acumuladores que essa razão não traz ganho adicional; os registradores extras ficam parados esperando a unidade funcional.

7. Compilador vs. hardware: quem extrai ILP?

Em -O0, o compilador traduz o código literalmente: cada variável é armazenada na pilha, cada acesso envolve mov de/para a memória. O hardware OoOE ainda tenta encontrar ILP, mas com instruções extras de load/store a cada iteração, o overhead é substancial. Nesse cenário, a diferença entre 1 e 4 acumuladores é visível (2,6× na Tarefa 03).

Com -O2: o compilador ajuda

O -O2 ativa dezenas de passes de otimização, incluindo:

  • Promoção de variáveis a registradores: o acumulador deixa de estar na pilha e vive em um registrador — elimina load/store a cada iteração.
  • Strength reduction: simplifica expressões como 3*i + 1.
  • Loop-invariant code motion: move cálculos que não mudam para fora do laço.
  • Desenrolamento parcial: pode desenrolar o laço 2× ou 4× e mesclar acumuladores internamente.

Com -O3: vetorização automática

O -O3 adiciona auto-vectorization: o compilador pode converter o laço escalar em instruções SIMD (SSE/AVX), processando 4 inteiros de 32 bits por instrução VPADDD (128 bits) ou 8 por instrução VPADDD ymm (256 bits).

Quando o compilador vetoriza o laço de acumulador único, ele efetivamente cria múltiplos acumuladores "sob o capô" (um por lane SIMD) — tornando a versão explícita de 4 acumuladores redundante. Essa é a razão pela qual, em -O2/-O3, a diferença entre as duas versões praticamente desaparece.

Atenção: nem sempre O3 é mais rápido que O2

O3 pode escolher uma estratégia de vetorização ou desenrolamento que não é ótima para um kernel específico. Possíveis causas: penalidades de alinhamento, pressão de registradores, ou heurísticas de custo imprecisas no compilador. A Tarefa 03 observa 0,030 s (O3) contra 0,026 s (O2) para o laço de múltiplos acumuladores — O3 ligeiramente mais lento, provavelmente por uma escolha de vetorização diferente.

1. Medição de tempo com clock_gettime

Símbolo / tipo Descrição Valor típico (Linux)
struct timespec Estrutura com tv_sec (segundos) e tv_nsec (nanossegundos) Definido em <time.h>
CLOCK_MONOTONIC Relógio monotônico (não afetado por NTP) Resolução ~1 ns
_POSIX_C_SOURCE 199309L Feature-test macro para habilitar clock_gettime Deve ser definido antes de qualquer #include
clock_gettime() Captura tempo de parede com resolução de nanosegundos Syscall ou vDSO 
#define _POSIX_C_SOURCE 199309L
#include <time.h>

static double agora(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}

double inicio = agora();
/* ... trecho a medir ... */
double tempo = agora() - inicio;
Por que clock_gettime e não clock()?

clock() mede CPU time (soma de todos os núcleos), com resolução de ~1 µs. clock_gettime(CLOCK_MONOTONIC) mede wall time com resolução de ~1 ns. Para programas paralelos (OpenMP), clock() produz resultados enganosos. A Tarefa 03 usa clock_gettime para precisão de nanossegundos.

3. Flags de compilação e seus efeitos

Flag Nível Otimizações relevantes para ILP
-O0 Nenhuma Tradução literal; variáveis na pilha; nenhum unroll
-O1 Básico Promoção a registradores; remoção de código morto
-O2 Padrão Loop unroll parcial; strength reduction; inlining
-O3 Agressivo Auto-vectorização SIMD; unroll agressivo
-march=native — Habilita instruções ISA do hardware local (AVX2, etc.)
-funroll-loops — Força desenrolamento de laços (pode aumentar código)

4. Padrões de laço para ILP

Acumulador único (cadeia RAW)

long long soma = 0;
for (long i = 0; i < n; ++i)
    soma += v[i];  // cadeia de N dependências

Múltiplos acumuladores (cadeias independentes)

long long s0 = 0, s1 = 0, s2 = 0, s3 = 0;
long i = 0;
for (; i + 3 < n; i += 4) {
    s0 += v[i];
    s1 += v[i + 1];
    s2 += v[i + 2];
    s3 += v[i + 3];
}
/* Tail: elementos restantes */
for (; i < n; ++i) s0 += v[i];
long long soma = s0 + s1 + s2 + s3;
Laço de cauda (tail loop)

Quando $N$ não é divisível por 4, o segundo for processa os últimos 0 a 3 elementos. Isso garante que a soma é correta para qualquer $N$.

5. Resumo executivo de fórmulas

Regras práticas — ILP e acumuladores
  • Acumuladores ideais = $\frac{\text{Latência}}{\text{Throughput recíproco}}$.
  • ADD inteiro: $\frac{1}{0{,}25} = 4$ acumuladores ideais.
  • ADDSD FP double: $\frac{4}{0{,}5} = 8$ acumuladores ideais.
  • Cadeia RAW: $T = N \times L$ ciclos (limitado pela latência).
  • $k$ cadeias independentes: $T \approx \frac{N}{k} \times L$ ciclos.
  • -O0: sem otimização → diferença entre estilos é máxima.
  • -O2/-O3: compilador pode gerar acumuladores e vetorizar → diferença diminui.
  • Use clock_gettime(CLOCK_MONOTONIC) para medição precisa de wall time.
  • Use gcc -S para inspecionar o assembly e confirmar vetorização.
