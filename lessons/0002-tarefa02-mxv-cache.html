1. Contexto e ponto de partida

Base teórica na Teoria 02

Poder computacional, Power Wall, Memory Wall e núcleos lógicos estão em Fundamentação teórica. Esta lição foca na prática: dissecção dos dois padrões de acesso e medição.

Muitos problemas reais exigem uma quantidade de cálculos impraticável para um único processador sequencial. Alguns exemplos:

  • Simulações de dinâmica molecular: modelar $10^{23}$ moléculas de uma proteína requer bilhões de interações a cada passo de tempo.
  • Previsão do tempo: o modelo ECMWF divide a atmósfera em $\sim10^9$ células 3D e recalcula temperatura, pressão e velocidade a cada minuto simulado.
  • Modelos de linguagem (LLMs como o Gemini): o treinamento de um modelo com 100 bilhões de parâmetros exige $>10^{23}$ operações de ponto flutuante.
  • Simulações físicas de alta energia: o detector LHC gera ~1 PB de dados por segundo, exigindo filtragem e análise em tempo real.

A multiplicação matriz-vetor (MxV) é o bloco fundamental de todos esses cálculos. Redes neurais são compostas de centenas de camadas lineares (cada uma é uma MxV) seguidas de ativações. Solucionadores de equações diferenciais iterativos (método de gradiente conjugado, GMRES) fazem uma MxV por iteração.

Antes de paralelizar, porém, é essencial entender onde o tempo vai na versão sequencial. A Tarefa 02 faz exatamente isso: mede a diferença entre dois padrões de acesso à memória que realizam a mesma computação — e revela que o gargalo é o barramento, não a CPU.

2. Dissecção de row_major.c

Cabeçalho e macros

#include <stdio.h>   // printf
#include <stdlib.h>  // malloc, calloc, free, atoi
#include <time.h>    // clock_t, clock(), CLOCKS_PER_SEC

Três headers da biblioteca padrão C. Não há dependências externas — o código compila em qualquer sistema POSIX com gcc row_major.c -o row_major.

Leitura do tamanho da matriz

int N = 2000;
if (argc > 1) N = atoi(argv[1]);

N = 2000 é o padrão. Passando um argumento na linha de comando (./row_major 4000), a função atoi converte a string do argv para inteiro. Isso permite medir o impacto do tamanho sem recompilar.

Alocação dinâmica da matriz e vetores

double *A = malloc((size_t)N * N * sizeof(double));
double *x = malloc(N * sizeof(double));
double *y = calloc(N, sizeof(double));
  • A: ponteiro para a matriz $N \times N$ armazenada como vetor 1-D (row-major). Para $N = 2000$: $2000^2 \times 8 = 32$ MB.
  • x: vetor de entrada, $N$ doubles = 16 KB para $N = 2000$.
  • y: vetor resultado, inicializado com zeros via calloc — equivalente a escrever um laço for com y[i] = 0.0, mas mais conciso e potencialmente mais rápido (implementado via memset internamente).
  • O cast (size_t) evita overflow para $N$ grande: se N = 50000, N*N = 2,5×109 estoura um int de 32 bits.

Inicialização dos dados

for (int i = 0; i < N * N; i++) A[i] = 1.0;
for (int i = 0; i < N; i++) x[i] = 1.0;

Todos os elementos são 1,0 para facilitar a verificação: o resultado esperado é y[i] = N para todo $i$. O laço de inicialização também “aquece” a memória, mapeando as páginas virtuais para páginas físicas (page fault de primeira escrita).

Medição de tempo e o kernel central

clock_t inicio = clock();

for (int i = 0; i < N; i++) {
    double s = 0.0;
    for (int j = 0; j < N; j++)
        s += A[i * N + j] * x[j];
    y[i] = s;
}

clock_t fim = clock();
double tempo = (double)(fim - inicio) / CLOCKS_PER_SEC;
  • Acumulador escalar s: cada iteração do laço $j$ faz uma multiplicação e uma adição (FMA). O resultado parcial fica em registrador — sem escrita na memória a cada passo.
  • A[i * N + j]: com $i$ fixo no laço externo, $j$ varia de 0 a $N-1$. Os endereços A + i*N + 0, A + i*N + 1, ..., A + i*N + N-1 são contíguos — acesso sequencial perfecto para o hardware prefetcher.
  • x[j]: o vetor $x$ (16 KB para $N=2000$) cabe em L1 cache, portanto é acessado sempre com latência mínima após a primeira volta do laço externo.
  • Escrita em y[i]: ocorre apenas uma vez por iteração de $i$ — mínimo de escritas.
Padrão de acesso row-major: cache-friendly

A cada miss em L1, uma linha de cache de 64 bytes = 8 doubles é carregada. Os próximos 7 acessos (A[i*N+j+1] até A[i*N+j+7]) já estão em cache — sem nova latência. Razão de miss: ~12,5%.

3. Dissecção de collum_major.c

O laço transposto

clock_t inicio = clock();

for (int j = 0; j < N; j++) {
    for (int i = 0; i < N; i++)
        y[i] += A[i * N + j] * x[j];
}

clock_t fim = clock();

A alocação, inicialização e medição são idênticas ao row_major.c. Apenas a ordem dos laços muda: o laço externo varre colunas ($j$) e o interno varre linhas ($i$).

Por que isso é desastroso para a cache?

O acesso A[i * N + j] com $j$ fixo e $i$ variando produz os endereços: 

A[0*N + j]   →  base + j*8
A[1*N + j]   →  base + (N+j)*8        // salto de N×8 bytes
A[2*N + j]   →  base + (2N+j)*8       // salto de N×8 bytes
...
A[(N-1)*N+j] →  base + ((N-1)N+j)*8  // salto de N×8 bytes

Para $N = 2000$, cada salto é de $2000 \times 8 = 16\,000$ bytes — 250 linhas de cache entre acessos consecutivos. A cache L1 (tipicamente 32–64 KB) não consegue manter 250 linhas simultaneamente: cada acesso expulsa as anteriores antes de serem reutilizadas.

Padrão de acesso column-major: cache-unfriendly

Cada acesso a A[i*N+j] provavelmente gera um cache miss em L1 e L2, forçando uma busca na DRAM (latência >200 ciclos). Razão de miss: ~100%.

Diferença de acumulador

No collum_major.c não há acumulador escalar local: y[i] += ... lê e escreve em y[i] a cada iteração do laço interno. O vetor y (16 KB) permanece em cache (pois é acessado sequencialmente no laço interno), mas o custo da matriz já é proibitivo.

4. Comparativo de desempenho e interpretação

Métrica Row-major Column-major
FLOPs realizados $2N^2$ (idêntico) $2N^2$ (idêntico)
Padrão de acesso a $A$ Sequencial (stride = 8 B) Strided (stride = $N\times8$ B)
L1 cache misses (estimado) $N^2/8$ $\approx N^2$
Tempo típico ($N=2000$) ~0,015 s ~0,080 s
Speedup observado 1,0× (baseline) ~5–10× mais lento

A diferença não vem de operações aritméticas a mais — o número de FLOPs é idêntico. Ela vem exclusivamente de onde os dados estão no momento do acesso. Esse é o princípio central do Memory Wall: a banda de memória, e não a potência da FPU, determina o desempenho.

5. Quizzes

Questão 1 de 4
Qual propriedade do hardware explica o fato de o acesso row-major ser muito mais rápido que o column-major em C, mesmo realizando o mesmo número de operações aritméticas?
Correto. Quando a cache carrega A[i*N+j], ela traz os próximos 7 doubles (A[i*N+j+1] a A[i*N+j+7]) gratuitamente na mesma linha. Em row-major, todos os 8 são usados nos próximos 7 passos do laço interno. Em column-major, o próximo acesso pula $N$ posições — a linha é carregada e descartada sem reuso.
Questão 2 de 4
Para $N = 2000$, qual é o stride (distância em bytes entre dois acessos consecutivos a $A$) no padrão column-major?
Correto. O acesso column-major percorre $i = 0, 1, \ldots, N-1$ com $j$ fixo, acessando A[0*N+j], A[1*N+j], ..., em endereços espaçados por $N \times 8 = 2000 \times 8 = 16\,000$ bytes — 250 linhas de cache entre acessos consecutivos.
Questão 3 de 4
A multiplicação matriz-vetor (MxV) é classificada como um algoritmo memory-bound. Qual afirmação melhor justifica essa classificação?
Correto. A intensidade aritmética é $I = 2N \text{ FLOPs} / (8N \text{ bytes}) = 0{,}25$ FLOP/byte. Uma banda de 100 GB/s entrega apenas $0{,}25 \times 100 = 25$ GFLOP/s efetivos — muito abaixo dos TFLOP/s de pico da FPU. O modelo Roofline confirma: a MxV fica no lado memory-bound.
Questão 4 de 4
Por que a tarefa usa calloc para alocar y[], mas malloc para A[] e x[]?
Correto. O vetor y acumula produtos parciais: y[i] += A[i*N+j] * x[j]. Se y contivesse lixo de memória, o resultado final seria incorreto. A e x são inicializados explicitamente com for antes de serem usados, portanto malloc é suficiente — o calloc seria apenas redundante.

1. O gargalo de von Neumann

A arquitetura de von Neumann, proposta em 1945, separa fisicamente a unidade de processamento (CPU) da memória principal (RAM). Toda instrução e todo dado precisam cruzar o barramento de memória para chegar à CPU. Esse canal é o principal estrangulamento de desempenho em programas modernos.

A CPU executa bilhões de operações por segundo (GHz), enquanto a RAM responde em dezenas ou centenas de nanosegundos. A diferença de velocidade entre processador e memória tem crescido desde os anos 1980 — documentada por Wulf e McKee em 1995 como o Memory Wall.

Memory Wall — ordem de grandeza
Componente Latência típica Largura de banda típica
Registrador < 0,3 ns (1 ciclo) centenas de GB/s (interno)
Cache L1 (32–64 KB) 1–4 ns (4–12 ciclos) 1–2 TB/s
Cache L2 (256 KB – 1 MB) 5–15 ns (12–40 ciclos) 200–500 GB/s
Cache L3 (8–64 MB) 30–60 ns (80–200 ciclos) 100–300 GB/s
RAM (DDR5) 60–100 ns (> 200 ciclos) 40–100 GB/s por canal

Para uma CPU a 3 GHz, cada ciclo dura ~0,33 ns. Um acesso a RAM que demora 80 ns representa 240 ciclos de espera — ciclos em que a unidade de execução fica parada aguardando dados.

2. Hierarquia de cache: L1, L2 e L3

Para atenuar o Memory Wall, os processadores modernos inserem bancos de memória SRAM (mais rápida que DRAM, mas menor e mais cara) em múltiplos níveis entre a CPU e a memória principal.

Funcionamento básico

Quando a CPU requisita um endereço, o hardware percorre a hierarquia do nível mais rápido para o mais lento:

  1. L1 hit: dado encontrado em L1 — resposta em ~4 ciclos.
  2. L2 hit: ausente em L1, encontrado em L2 — resposta em ~12–40 ciclos.
  3. L3 hit: ausente em L1 e L2, encontrado em L3 — resposta em ~80–200 ciclos.
  4. Cache miss (DRAM): ausente em todos os níveis — resposta em > 200 ciclos.

Linhas de cache de 64 bytes

O hardware não transfere bytes individuais; transfere linhas de cache inteiras de 64 bytes = 8 doubles entre níveis. Quando o dado no endereço $A$ é requisitado, os bytes $A$ até $A+63$ são todos carregados para a cache.

Isso cria dois princípios fundamentais:

  • Localidade temporal: um dado acessado recentemente provavelmente será acessado novamente. Mantê-lo em cache é benéfico.
  • Localidade espacial: quando um dado é acessado, vizinhos na memória provavelmente também serão. Carregar 64 bytes antecipa esses acessos.
$$\text{Dados por linha} = \frac{64 \text{ bytes}}{8 \text{ bytes/double}} = 8 \text{ doubles}$$

3. Acesso row-major vs. column-major na MxV

C armazena arrays multidimensionais em ordem row-major: os elementos de uma mesma linha são contíguos na memória. Para uma matriz $N \times N$ mapeada em array 1-D, o elemento $A[i][j]$ fica no endereço base A + i*N + j.

Row-major (acesso sequencial — cache-friendly)

O laço interno percorre $j$ enquanto $i$ é fixo: A[i*N+0], A[i*N+1], ..., A[i*N+N-1]. Esses endereços são contíguos. Um único carregamento de linha de cache traz 8 doubles usados nos próximos 7 passos. A taxa de miss tende a $\frac{1}{8}$ miss/operação — próxima do mínimo físico.

Column-major (acesso strided — cache-unfriendly)

O laço externo percorre $j$ enquanto o interno percorre $i$: A[0*N+j], A[1*N+j], ..., A[(N-1)*N+j]. Cada acesso consecutivo pula $N$ posições (stride de $N \times 8$ bytes). Para $N = 2000$, o stride é 16 000 bytes — 250 linhas de cache entre acessos consecutivos. Cada acesso a $A[i \cdot N + j]$ resulta provavelmente em um cache miss compulsório em L1 e L2.

$$\text{Stride}_{\text{col}} = N \times 8 \text{ bytes} \xrightarrow{N=2000} 16\,000 \text{ bytes} = 250 \text{ linhas de cache}$$

Impacto em contagem de misses

Ordem de acesso L1 misses estimados Razão de misses
Row-major (sequencial) $N^2 / 8$ ~12,5% (1 miss a cada 8 acessos)
Column-major (strided) $\approx N^2$ ~100% (1 miss por acesso)

4. Saturação de barramento e modelo Roofline

A MxV é um algoritmo memory-bound: para cada linha da matriz, realiza $2N$ FLOPs lendo $8N$ bytes ($N$ doubles de $A$ mais reutilização de $x$). A intensidade aritmética é:

$$I = \frac{2N \text{ FLOPs}}{8N \text{ bytes}} = 0{,}25 \text{ FLOP/byte}$$

O modelo Roofline impõe que o desempenho real não pode superar:

$$\text{Desempenho}_{\max} = \min\!\left(P_{\text{pico}},\; I \times B_{\text{mem}}\right)$$

Para $B_{\text{mem}} = 100$ GB/s: $I \times B = 0{,}25 \times 100 = 25$ GFLOP/s. Mesmo com 1 TFLOP/s de pico da CPU, a MxV atinge no máximo ~25 GFLOP/s — ditado pelo barramento, não pela ALU.

Prefetching e hardware stream prefetchers

Processadores modernos detectam acessos sequenciais e pré-carregam linhas de cache antes de serem requisitadas. Para acessos row-major, o prefetcher funciona eficientemente. Para strides grandes (column-major), ele falha ou age tarde demais para ocultar a latência.

5. NUMA e impacto em HPC

Nos nós do cluster NPAD/UFRN, a arquitetura é NUMA (Non-Uniform Memory Access). Cada soquete tem sua memória local; o acesso ao soquete remoto atravessa a interconexão QPI/UPI com latência maior. Para programas memory-bound como a MxV, a afinidade de memória pode representar uma penalidade de 20–40%.

$$\text{Latência}_{\text{remoto}} \approx 1{,}3 \times \text{Latência}_{\text{local}}$$

Políticas como OMP_PROC_BIND=close e numactl --localalloc garantem que os dados sejam alocados no mesmo soquete das threads que os acessam.

6. Medição de tempo: clock() vs. clock_gettime()

Função O que mede Resolução típica Quando usar
clock() CPU time (soma de todos os núcleos) ~1 ms (CLOCKS_PER_SEC = 10⁶) Comparação de esforço CPU em sequencial
clock_gettime(CLOCK_MONOTONIC) Tempo de parede (wall time) ~1 ns HPC, benchmarking preciso, OpenMP

Em versões paralelas com OpenMP, clock() soma o tempo de todos os núcleos e produz resultado enganoso. Use omp_get_wtime() ou clock_gettime(CLOCK_MONOTONIC) nesses casos.

Por que (size_t)N * N?

Se N é int (32 bits) e $N = 50\,000$, então N * N = 2.5 × 10⁹ estoura um int com sinal. O cast (size_t) garante aritmética de 64 bits antes da multiplicação.

5. Resumo executivo de fórmulas

Regras práticas — MxV e cache
  • Linha de cache = 64 bytes = 8 doubles.
  • Row-major: 1 miss a cada 8 acessos à matriz $A$ ($\approx 12{,}5\%$).
  • Column-major: ~1 miss por acesso ($\approx 100\%$).
  • Stride column-major: $N \times 8$ bytes ($= 16\,000$ B para $N=2000$).
  • Intensidade aritmética MxV: $I = 0{,}25$ FLOP/byte.
  • Teto de desempenho (Roofline): $I \times B_{\text{mem}}$ GFLOP/s.
  • Cast (size_t) antes de multiplicar dimensões grandes.
  • Use calloc para vetores que devem começar em zero.
