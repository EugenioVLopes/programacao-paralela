Licao sobre pi estocastico, rand e false sharing

Tarefa 08 com 4 versoes em tarefa08 pi ponto c. Critical contra vetor, rand contra rand_r.

1. O problema em 30 segundos

Sorteie N pontos x, y uniformes em menos 1 a 1. Conte N dentro do circulo x ao quadrado mais y ao quadrado menor ou igual a 1. Entao pi vale cerca de 4 vezes N dentro sobre N, com erro perto de 1 sobre raiz de N. O metodo e paralelo por natureza. O desafio e somar acertos sem serializar.

Voce vai construir 4 programas.

  • V1 usa contador privado com critical e rand
  • V2 usa vetor hits por id e rand
  • V3 usa contador privado com critical e rand_r
  • V4 usa vetor hits por id e rand_r

Depois compare tempos e explique com coerencia MESI. Eu gosto dessa tarefa porque ela pune o descuido na hora. Mais threads deixam o codigo ruim mais lento, nao mais rapido.

Por que isso importa
Poder computacional e resolver problema grande rapido, como clima, genoma, IA e CFD. Frequencia parou perto de 4 GHz. Mais GHz derrete o chip, pela relacao P perto de C vezes V ao quadrado vezes f. A saida foi usar varios nucleos logicos em paralelo. Essa tarefa mostra que paralelizar sem entender cache e gerador aleatorio gera slowdown, nao speedup.

2. Disseccao linha a linha

V1 com privada, critical e rand

srand(12345); // estado global unico, todas disputam
#pragma omp parallel shared(total,N) default(none)
{
  long local = 0; // pilha privada, sem MESI, sem lock
  #pragma omp for
  for (i=0;i<N;i++) {
    double x = (double)rand()/RAND_MAX*2.0-1.0; // lock interno aqui
    if (x*x+y*y <= 1.0) local++; // barato, registrador
  }
  #pragma omp critical
  total += local; // 1 vez por thread, custo O de p
}

Rand guarda estado global com lock. Cada ponto vira trecho serial. O critical final roda uma vez por thread. Ele nao e o vilao.

V2 com vetor compartilhado e rand

long *hits = calloc(P,sizeof(long)); // P longs cabem em 1 linha de 64B
int tid = omp_get_thread_num();
if (hit) hits[tid]++; // escrita por acerto, MESI dispara
for (i=0;i<P;i++) total+=hits[i]; // soma serial apos regiao

V3 e v4 trocam rand por rand_r

unsigned int seed = 12345u + 7919u*(unsigned int)omp_get_thread_num();
double x = (double)rand_r(&seed)/RAND_MAX*2.0-1.0; // estado na pilha, sem lock

Seeds distintas evitam sequencias iguais, que viciariam pi. Eu uso 7919 para espacar as subsequencias do LCG.

Cura do falso compartilhamento

typedef struct { long v; char pad[64-sizeof(long)]; } Slot __attribute__((aligned(64)));

Cada hits por id ganha linha exclusiva. Da no mesmo usar acumulador local com uma escrita, ou reduction com mais total.

3. O que eu medi de verdade

Compile com gcc menos O2 menos fopenmp menos Wall, com menos lm no fim. Rode com OMP_NUM_THREADS igual a 1, 2, 4 e 8 e N igual a 2000000.

thr v1 crit rand v2 vet rand v3 crit rand_r v4 vet rand_r v4 pad
1 0,095s 0,101s 0,023s 0,036s 0,036s
2 0,287s 0,416s 0,013s 0,023s 0,019s
4 0,343s 0,344s 0,007s 0,012s 0,011s
8 0,572s 0,682s 0,004s 0,014s 0,006s

V1 e v2 ficam lentos e pioram com p. O lock do rand domina. O vetor nao ajuda nem atrapalha muito, fica mascarado.

V3 escala, com ganho de 5,5 vezes em 8 threads. Sem estado global, o unico serial e 1 critical por thread.

V4 fica pior que v3 e degrada em 8 threads. MESI puro aparece. Pad recupera 2,4 vezes, de 0,014 para 0,006s.

Frase para o relatorio
Com rand o gargalo e software, lock global. Com rand_r o gargalo vira hardware, MESI no vetor. So contador privado com rand_r escala. Vetor colado pede padding.

4. Quizzes para fixar

Questao 1 de 2
Por que v1 e v2 com rand ficam mais lentos com mais threads?
Correto. Rand guarda estado global com lock. Cada ponto vira trecho serial. O critical roda 1 vez por thread e nao pesa.
Questao 2 de 2
Por que v4 com rand_r e mais lenta que v3 e o padding cura?
Correto. Hits por id a cada acerto poe 8 contadores na mesma linha de 64 bytes. Cada escrita invalida vizinhos por MESI. Padding isola linhas.
