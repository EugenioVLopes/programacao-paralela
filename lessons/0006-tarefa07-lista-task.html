Lição 06: Task OpenMP. Processamento de lista encadeada

Tarefa 07 • Análise de tarefa07.c • Processamento paralelo com #pragma omp task

1. O problema

O programa constrói uma lista encadeada com nomes de arquivos fictícios e processa cada nó em paralelo usando #pragma omp task.

O objetivo central é determinar quantas vezes cada nó é processado e garantir que nenhum item seja duplicado ou omitido.

2. Estrutura de dados do nó

typedef struct Node {
    char filename[256];
    struct Node *next;
} Node;
  • filename: armazena a cadeia de caracteres com o nome do arquivo.
  • next: armazena o endereço de memória do nó seguinte da lista.

3. Funções de criação e inserção

Criação de nó

Node *create_node(const char *filename) {
    Node *new_node = (Node *)malloc(sizeof(Node));
    strncpy(new_node->filename, filename, 255);
    new_node->filename[255] = '\0';
    new_node->next = NULL;
    return new_node;
}

Inserção no início

void insert_at_beginning(Node **head, const char *filename) {
    Node *new_node = create_node(filename);
    new_node->next = *head;
    *head = new_node;
}

Inserção no final

void insert_at_end(Node **head, const char *filename) {
    Node *new_node = create_node(filename);
    if (*head == NULL) {
        *head = new_node;
        return;
    }
    Node *current = *head;
    while (current->next != NULL) {
        current = current->next;
    }
    current->next = new_node;
}

4. Processamento paralelo com tarefas

Padrão estruturado com single, task e taskwait

void process_list_parallel(Node *head) {
    #pragma omp parallel
    {
        #pragma omp single
        {
            Node *current = head;
            while (current != NULL) {
                #pragma omp task firstprivate(current)
                {
                    int tid = omp_get_thread_num();
                    printf("Arquivo: %s | Thread ID: %d\n",
                           current->filename, tid);
                }
                current = current->next;
            }
        }
        #pragma omp taskwait
    }
}

Papel de firstprivate(current)

  • O ponteiro current avança a cada iteração do laço sequencial.
  • Sem firstprivate, as tarefas compartilham a referência e leem NULL quando o laço encerra.
  • A cláusula firstprivate(current) copia o valor exato do ponteiro no instante de criação da tarefa.

Papel de single

  • Sem single, todas as threads do time executam o laço de travessia.
  • Cada thread percorreria a lista completa, gerando $N \times T$ tarefas.
  • A diretiva single restringe a travessia a uma única thread produtora.

Papel de taskwait

  • O encerramento do bloco single não bloqueia tarefas assíncronas pendentes.
  • A diretiva taskwait estabelece uma barreira explícita para as tarefas filhas geradas no contexto.

5. Função principal

int main() {

7. Reflexão sobre a contagem de execuções

Com a combinação de single e task, cada nó é processado exatamente uma vez:

  1. A diretiva single assegura que apenas uma thread percorra a lista.
  2. Cada iteração instancia exatamente uma tarefa para o nó correspondente.
  3. O runtime distribui as tarefas entre as threads do time, executando cada tarefa uma única vez.
Resultado operacional: uma lista com $N$ nós gera $N$ tarefas distintas. Cada nó é exibido uma única vez.

Fatores não-determinísticos entre execuções

  • A thread responsável pela execução de cada tarefa.
  • A ordem temporal em que as tarefas completam o processamento.
  • O tempo total de execução.

Fatores determinísticos

  • A quantidade total de processamentos por nó, mantida estritamente em uma execução por nó.
  • Os dados lidos do campo filename de cada elemento.

9. Paralelismo de laço vs. paralelismo de tarefas

Base teórica na Teoria 07

Barreira térmica e multicore estão em Fundamentação teórica. Aqui: por que lista encadeada pede tasks.

Diferença entre paralelismo de laço e paralelismo de tarefas

A diretiva parallel for requer contadores de iteração com limites pré-computáveis. Em estruturas dinâmicas como listas encadeadas, o comprimento total só é descoberto durante a travessia.

A diretiva task resolve esse cenário ao desacoplar a geração das tarefas de sua execução pelas threads disponíveis.

10. Questionário de fixação

1. Qual é a função da diretiva single no percurso da lista?

  1. Dividir o vetor igualmente entre as threads disponíveis na região
  2. Garantir que apenas uma thread percorra os nós e instancie as tarefas
  3. Acelerar o acesso aos blocos de memória alocados na pilha do processo

2. O que ocorre quando a travessia é feita em parallel sem single?

  1. Cada nó é processado uma única vez pela thread mestre da região
  2. Cada nó é processado $T$ vezes, gerando $N \times T$ tarefas no total
  3. O programa interrompe a execução com erro de compilação imediato

3. Qual é a finalidade da diretiva taskwait?

  1. Aguardar a conclusão de todas as tarefas geradas no contexto atual
  2. Distribuir novas tarefas adicionais para núcleos que estejam livres
  3. Elevar a prioridade de escalonamento das tarefas no pool de execução

4. Por que a cláusula firstprivate(current) é necessária?

  1. Para permitir escrita concorrente no mesmo ponteiro por várias threads
  2. Para copiar o valor de current no instante exato de criação da tarefa
  3. Para liberar a memória alocada dinamicamente pelo nó de forma automática

Fundamentação teórica

Teoria, modelagem matemática e contexto de HPC integrados à prática desta tarefa.

1. Motivação: Por que task para listas?

As diretivas parallel for e parallel sections exigem que o paralelismo seja conhecido em tempo de compilação. O OpenMP divide os índices do laço entre as threads antes da execução começar. Isso funciona bem para iterações de laço, mas listas encadeadas não são arranjos contíguos: o compilador não sabe quantos nós existem até o programa percorrer a lista em tempo de execução.

A diretiva #pragma omp task resolve esse problema ao criar tarefas explícitas em tempo de execução. Cada nó da lista gera uma tarefa; o sistema de tarefas do OpenMP — não o programador — decide qual thread executa qual tarefa.

Ideia central: O task separa a criação da execução. Você gera todas as tarefas primeiro; o task runtime as distribui entre as threads disponíveis.

2. Anatomia de uma #pragma omp task

#pragma omp task [clause [, clause]...]
// código da tarefa — pode ser um bloco ou uma única instrução
{
    // região paralela: só uma thread cria a tarefa; outra thread pode executá-la
    printf("Arquivo: %s | Thread: %d\n", node->filename, omp_get_thread_num());
}

Cláusulas disponíveis

CláusulaEfeito
shared(list) Variáveis na list são compartilhadas entre todas as tarefas e a thread que as criou.
private(list) Cada tarefa obtém uma cópia não inicializada da variável. O valor original não é visível dentro da tarefa.
firstprivate(list) Como private, mas cada cópia é inicializada com o valor da variável no momento da criação da tarefa.
final(expression) Se expression for verdadeira, todas as tarefas internas são geradas como included (executadas inline pela thread atual).
depend(dependence-type: list) Especifica dependências entre tarefas (tipo in, out, inout) para ordenação.
priority(value) Define a prioridade de agendamento da tarefa. Valores maiores têm preferência.

Ciclo de vida de uma tarefa

  1. Criação (encoding): A thread que encontra o task empacota o contexto (valores das variáveis no momento) em um descriptor e o entrega ao task runtime.
  2. Agendamento (scheduling): O runtime atribui a tarefa a uma thread do time. Uma thread pode criar tarefas e outra executá-las.
  3. Execução (execution): A thread designada executa o corpo da tarefa.
  4. Junção (join): O taskwait aguarda a conclusão de todas as tarefas pendentes geradas pela região atual.
Ponto crucial: A thread que cria a tarefa (task) pode ser diferente da thread que a executa. Isso é o inverso do parallel for, onde a thread que itera é a que executa.

3. O problema central: cada nó é processado quantas vezes?

O comportamento do processamento de lista com tarefas depende de como o laço de travessia é escrito. Existem três padrões principais:

Padrão A — Laço dentro da região paralela (INCORRETO)

#pragma omp parallel
{
    // PROBLEMA: todas as threads executam o laço completo
    Node *current = head;
    while (current != NULL) {
        #pragma omp task
        {
            printf("%s\n", current->filename);
        }
        current = current->next;
    }
}
  • Todas as threads entram na região paralela.
  • Cada thread percorre a lista inteira.
  • Cada nó é processado por tantas vezes quantas forem as threads do time.
  • Resultado: $N$ nós × $T$ threads execuções.

Padrão B — Laço fora da região paralela, single no laço (CORRETO)

#pragma omp parallel
{
    #pragma omp single
    {
        Node *current = head;
        while (current != NULL) {
            #pragma omp task
            {
                printf("%s | thread %d\n",
                       current->filename, omp_get_thread_num());
            }
            current = current->next;
        }
    }
    #pragma omp taskwait
}
  • Apenas uma thread executa o laço de travessia.
  • Essa thread cria uma tarefa por nó.
  • O runtime distribui as tarefas entre as threads do time.
  • O taskwait garante que todas as tarefas terminem antes das threads saírem da região.

Padrão C — Travessia sequencial antes da região paralela (alternativa)

// Primeira percorrida: contar nós (sequencial)
int node_count = 0;
Node *count = head;
while (count) { node_count++; count = count->next; }

// Alocar vetor de ponteiros (paralelo, task-based)
Node **nodes = (Node **)malloc(node_count * sizeof(Node *));
Node *fill = head;
for (int i = 0; i < node_count; i++) {
    nodes[i] = fill;
    fill = fill->next;
}

#pragma omp parallel for
for (int i = 0; i < node_count; i++) {
    process_node(nodes[i]);
}
  • Converte a lista em vetor primeiro; depois usa parallel for — evita o problema inteiramente.
  • Custo: $O(N)$ adicional sequencial para contar e copiar ponteiros.

4. Por que o comportamento varia entre execuções?

O task runtime do OpenMP é não-determinístico por design. O agendador pode escolher qualquer thread disponível para cada tarefa. Isso significa:

  • A ordem em que as tarefas são executadas varia entre execuções.
  • Se cada tarefa escrever em um acumulador compartilhado (por exemplo, count++), o valor final depende da ordem de interleaving — race condition.
  • Se cada tarefa escrever em uma posição distinta do vetor (por exemplo, results[i] = ...), não há race condition, mas a ordem de preenchimento é arbitrária.
Race condition vs. resultado variável: Quando cada nó é processado exatamente uma vez, mas a ordem varia, o resultado final pode ser diferente entre execuções se as tarefas escreverem na mesma variável compartilhada. Esse é o padrão da Tarefa 06 (Monte Carlo).

5. taskwait: aguardando todas as tarefas

O taskwait é uma barreira implícita para todas as tarefas geradas no bloco de código que o contém. Sem ele, as threads podem sair da região paralela antes que as tarefas terminem. 

#pragma omp parallel
{
    #pragma omp single
    {
        while (current != NULL) {
            #pragma omp task shared(current)
            {
                process_node(current);
            }
            current = current->next;
        }
    }
    // taskwait aqui: aguarda todas as tarefas criadas no single acima
    #pragma omp taskwait

    // Aqui, todas as tarefas já terminaram
    printf("Fim do processamento.\n");
}

Variantes de sincronização

DiretivaEfeito
taskwait Aguarda todas as tarefas filhas diretas do contexto atual.
taskgroup + taskwait Aguarda todas as tarefas de um grupo inteiro, incluindo tarefas aninhadas.
taskyield cede a thread corrente para que o scheduler possa executar outra tarefa pronta.

6. single: uma única thread no bloco

A diretiva #pragma omp single faz com que exatamente uma thread execute o bloco. As outras threads do time esperam no fim do bloco (barreira implícita), a menos que a cláusula nowait seja usada. 

#pragma omp single nowait
{
    // Apenas uma thread entra aqui; as outras passam direto
    Node *current = head;
    while (current != NULL) {
        #pragma omp task firstprivate(current)
        {
            printf("%s\n", current->filename);
        }
        current = current->next;
    }
}
// Se usasse nowait, as outras threads não esperariam o single terminar
// — perigoso se o código abaixo dependesse dos nós já estarem processados
firstprivate(current): Cada tarefa recebe sua própria cópia de current com o valor que current tinha quando a tarefa foi criada. Sem isso, todas as tarefas veriam o valor final de current após o laço terminar (provavelmente NULL).

7. omp_get_thread_num(): qual thread executa?

A função omp_get_thread_num() retorna o ID da thread que a chama, no intervalo [0, omp_get_num_threads() - 1]. 

int tid = omp_get_thread_num();    // ID da thread [0, T-1]
int nt  = omp_get_num_threads();   // total de threads no time

No Padrão B (correto), cada nó gera uma tarefa. Quando a thread 0 (ou qualquer thread designada pelo single) cria as tarefas, ela passa por cada nó e gera uma tarefa. As tarefas são então agendadas para as threads disponíveis — tipicamente de forma work-stealing: threads ociosas "roubam" tarefas de threads ocupadas.

Em uma execução típica com 4 threads, ao criar 10 tarefas, a thread 0 pode criar todas, mas as threads 1, 2 e 3 roubam tarefas para executar. A distribuição exata depende do scheduler e da carga de cada thread — e varia entre execuções.

1. Como as tasks funcionam por dentro

Quando você escreve #pragma omp task, não está apenas "criando uma thread extra". Você está inserindo uma unidade de trabalho em uma fila de tarefas mantida pelo runtime do OpenMP. Essa fila é global ao time de threads.

O modelo operacional é o work-stealing (roubo de trabalho):

  1. Fila local: cada thread possui uma fila privada de tarefas prontas para executar.
  2. Criação: quando uma thread encontra um task, ela empilha essa tarefa em sua própria fila.
  3. Execução: a thread executa suas próprias tarefas da pilha.
  4. Roubo: se uma thread fica ociosa (sua pilha vazia), ela "rouba" tarefas do fundo da pilha de outra thread que está ocupada.
Por que isso importa: a thread que cria a tarefa não é necessariamente a que a executa. A atribuição depende do estado das pilhas no momento exato — e esse estado varia a cada execução.

Em uma execução, a thread 0 pode criar 10 tarefas e executar 7 delas. Na próxima execução, com as mesmas entradas, a thread 0 pode executar apenas 3, porque as threads 1 e 2 roubaram mais cedo. Isso é correto e esperado.

2. Experimento A: "Quem são as threads deste time?"

Antes de trabalhar com tasks, confirme que você consegue identificar as threads do time.

Código descartável

Crie um arquivo exp_a_threads.c separado do projeto principal:

#include <stdio.h>
#include <omp.h>

int main() {
    #pragma omp parallel
    {
        int tid = omp_get_thread_num();
        int nt  = omp_get_num_threads();
        printf("Sou a thread %d de %d\n", tid, nt);
    }
    return 0;
}

O que fazer

  1. Compile: gcc -Wall -fopenmp -o exp_a_threads exp_a_threads.c
  2. Execute várias vezes com OMP_NUM_THREADS=4 ./exp_a_threads
  3. Observe: as mensagens aparecem sempre? A ordem muda?
O que observar: o número total de mensagens é sempre igual ao número de threads? Existe thread 0? Existe thread 3? Alguma thread nunca aparece? Isso confirma que o time está completo.

3. Experimento B: O que single faz sozinho?

Antes de combinar single com task, observe o comportamento do single isolado. 

int main() {
    #pragma omp parallel
    {
        #pragma omp single
        {
            printf(" single executado pela thread %d\n",
                   omp_get_thread_num());
        }
        printf("  fora do single, thread %d\n",
               omp_get_thread_num());
    }
    return 0;
}

Pergunta orientadora

Quantas vezes a mensagem do single aparece? E quantas vezes aparece a mensagem "fora do single"? Se você adicionar nowait ao single, o que muda na ordem das mensagens?

Insight: sem nowait, as outras threads esperam no fim do bloco single antes de continuar. Isso significa que, enquanto uma thread percorre a lista criando tasks, as outras ficam paradas aguardando — mas o runtime pode reaproveitá-las para executar tarefas roubadas.

4. Experimento C: O erro catastrófico de shared(current)

Este é o experimento mais importante da lição. Ele demonstra por que firstprivate(current) é obrigatório. 

int main() {
    int i = 0;
    #pragma omp parallel
    {
        #pragma omp single
        {
            for (i = 0; i < 5; i++) {
                // ERRADO DE PROPOSITO: shared captura o valor FINAL após o laço
                #pragma omp task shared(i)
                {
                    int tid = omp_get_thread_num();
                    printf("Task: i=%d | Thread: %d\n", i, tid);
                }
            }
        }
        #pragma omp taskwait
    }
    return 0;
}

O que fazer

  1. Compile e execute várias vezes.
  2. Anote o valor de i impresso em cada tarefa.
  3. Todas as tarefas imprimem o mesmo valor? Qual valor?
Por que acontece: com shared(i), todas as tarefas apontam para a mesma variável i. O laço for incrementa i rapidamente até 5. Quando as tarefas finalmente começam a executar (roubadas por outras threads), i já vale 5. Resultado: todas as tarefas imprimem i=5 (ou um valor inconsistente, dependendo do timing).

Correção

Substitua shared(i) por firstprivate(i). Recompile e execute novamente. Agora cada tarefa imprime o valor que i tinha no momento da criação.

5. Experimento D: Sem single, cada tarefa é criada T vezes

Este experimento replica o erro da Tarefa 07 quando o laço de travessia fica diretamente dentro de parallel. 

int main() {
    int count = 0;  // contador compartilhado (SERA USADO PARA OBSERVAR)
    #pragma omp parallel
    {
        int tid = omp_get_thread_num();
        for (int i = 0; i < 3; i++) {
            #pragma omp task firstprivate(i) shared(count)
            {
                #pragma omp atomic
                count++;
                printf("T%d criou task i=%d | Total count=%d\n",
                       tid, i, count);
            }
        }
    }
    printf("Valor final de count: %d\n", count);
    return 0;
}

Pergunta orientadora

Se executar com OMP_NUM_THREADS=4, qual o valor esperado de count se cada thread cria 3 tasks? E qual valor você vê? A relação é count = 3 iteracoes x T threads?

Como corrigir: envolva o for dentro de um #pragma omp single. Agora apenas uma thread (qualquer uma) cria as 3 tasks. O count final será exatamente 3.

6. Experimento E: taskwait vs. término prematuro

Este experimento demonstra o que acontece quando você remove o taskwait e a região paralela termina antes das tarefas. 

int main() {
    printf("Inicio da regiao paralela\n");
    #pragma omp parallel
    {
        #pragma omp single
        {
            for (int i = 0; i < 8; i++) {
                #pragma omp task firstprivate(i)
                {
                    printf("  [Task i=%d] Iniciando na thread %d\n",
                           i, omp_get_thread_num());
                    // Simula trabalho demorado
                    for (volatile int j = 0; j < 100000000; j++);
                    printf("  [Task i=%d] Terminou na thread %d\n",
                           i, omp_get_thread_num());
                }
            }
        }
        // REMOVA O TASKWAIT PARA VER O EFEITO
        // #pragma omp taskwait
    }
    printf("Fim da regiao paralela\n");
    return 0;
}

O que observar

  1. Execute sem taskwait. Note se a mensagem "Fim da regiao paralela" aparece antes de todas as tasks terminarem.
  2. Adicione #pragma omp taskwait depois do single. A mensagem "Fim" agora só aparece após todas as tasks.
Cuidado: sem taskwait, se a main termina logo após a região paralela, as threads do time são destruídas e tarefas pendentes podem ser canceladas ou deixadas inacabadas. O comportamento é indefinido pela especificação.

7. Experimento F: Observando o work-stealing na prática

Crie um experimento onde uma única thread gera muitas tarefas que "dormem" um pouco. Isso força as outras threads a roubarem trabalho. 

#include <unistd.h>  // para sleep()

int main() {
    #pragma omp parallel
    {
        #pragma omp single
        {
            for (int i = 0; i < 12; i++) {
                #pragma omp task firstprivate(i)
                {
                    int tid = omp_get_thread_num();
                    printf("[Task %2d] Executada pela thread %d\n", i, tid);
                    sleep(1);  // 1 segundo de "trabalho"
                }
            }
        }
        #pragma omp taskwait
    }
    return 0;
}

O que observar

  1. Execute com OMP_NUM_THREADS=4 ./exp_f_workstealing
  2. A thread 0 cria todas as 12 tasks, mas imprime a thread que executa cada uma.
  3. Na primeira execução, talvez thread 0 execute tasks 0, 1, 2... e as outras "roubem" tardiamente.
  4. Na segunda execução, a distribuição pode ser completamente diferente.
Contagem de tarefas por thread: adicione um array tasks_per_thread[NT] (onde NT é o número de threads) e incremente atomicamente dentro de cada task. No fim, imprima quantas tasks cada thread executou. Varia entre execuções?

8. Mapa mental: decisões na Tarefa 07

Quando for implementar a Tarefa 07, você precisa tomar três decisões:

DecisãoOpção erradaOpção corretaPor quê
Quem percorre a lista? Todas as threads Apenas uma (single) Evita criar N×T tarefas
Como capturar o nó atual? shared(current) firstprivate(current) Cada tarefa fixa o ponteiro no momento da criação
Quando liberar as threads? Região paralela acaba taskwait antes do fim Garante que todas as tarefas terminem

9. Quiz

1. No modelo work-stealing, uma thread ociosa pode:

  1. Roubar tarefas de outra thread ocupada
  2. Criar novas threads extras
  3. Terminar o programa mais cedo

2. Se uma task usa shared(i) e i é incrementado em um laço antes das tasks executarem, o valor de i visto pela task será:

  1. O valor de i no momento exato da execução da task
  2. O valor final de i após o laço terminar — provavelmente lixo para a lógica
  3. Sempre zero, porque i é reinicializado

3. Sem taskwait no fim da região paralela:

  1. Threads podem ser destruídas com tarefas pendentes
  2. Tasks são automaticamente serializadas
  3. O programa sempre gera erro de compilação

4. Com single + task, cada nó da lista é processado:

  1. Uma vez por cada thread do time
  2. Exatamente uma vez, por uma thread qualquer
  3. Apenas pela thread 0
