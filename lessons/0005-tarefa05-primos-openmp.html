Lição 05: Race Conditions ao Paralelizar Laços

Tarefa 05 • Dissecção de tarefa05.c • Observação de estado compartilhado

1. O problema

O programa conta primos no intervalo $[2, N]$. O teste de cada número não depende do teste de nenhum outro número. Cada iteração opera de forma isolada.

2. Dissecção de tarefa05.c

Versão sequencial

long total_primos_sequencial = 0;
for (long numero_atual = 2; numero_atual <= limite_superior; ++numero_atual) {
    if (eh_primo(numero_atual)) {
        total_primos_sequencial++;
    }
}
  • Uma thread percorre todos os números de 2 até o limite superior.
  • O resultado é correto: 348.513 primos para $N = 5.000.000$.

Versão paralela (sem alterar a lógica)

long total_primos_paralelo = 0;
#pragma omp parallel for
for (long numero_atual = 2; numero_atual <= limite_superior; ++numero_atual) {
    if (eh_primo(numero_atual)) {
        total_primos_paralelo++;
    }
}
  • O OpenMP divide os índices entre as threads.
  • Todas as threads escrevem na mesma variável total_primos_paralelo.
  • A CPU executa total_primos_paralelo++ em três passos: LOAD, ADD, STORE.
  • Duas threads leem o mesmo valor ao mesmo tempo. Ambas somam 1. Ambas gravam o mesmo resultado. O programa perde um incremento.
  • O resultado fica incorreto. O programa não gera erro visível.

O que observar

  • Correção: A contagem da versão paralela difere da sequencial. Isso é a race condition.
  • Distribuição de carga: Números maiores exigem mais divisões no teste de primalidade. A thread que recebe os números maiores gasta mais ciclos. As outras ficam ociosas.

3. Quizzes

Questão 1 de 2
Por que a versão paralela retorna um total de primos menor que a versão sequencial?
Correto. A operação total_primos_paralelo++ envolve LOAD, ADD e STORE. Threads que executam o LOAD ao mesmo tempo leem o mesmo valor e sobrescrevem o resultado uma da outra.
Questão 2 de 2
Por que a thread com os números maiores gasta mais tempo que as outras?
Correto. A função eh_primo testa divisores até $\sqrt{n}$. Números maiores exigem mais iterações internas. A thread com esses números gasta mais ciclos de CPU.

Fundamentação teórica

Teoria, modelagem matemática e contexto de HPC integrados à prática desta tarefa.

1. Paralelismo de laços

A maioria dos programas numéricos gasta tempo em laços. O OpenMP distribui as iterações de um laço entre as threads disponíveis.

A diretiva #pragma omp parallel for cria as threads e divide os índices. Com 1000 iterações e 4 threads, o escalonamento estático atribui 250 iterações a cada thread.

2. Race conditions

Uma race condition ocorre quando threads escrevem na mesma variável sem sincronização. O hardware sobrepõe as operações e corrompe o resultado.

A CPU executa total_primos_paralelo++ em três passos:

  1. LOAD: A CPU lê o valor da memória para o registrador.
  2. ADD: A CPU soma 1 no registrador.
  3. STORE: A CPU grava o resultado na memória.

Duas threads executam o LOAD ao mesmo tempo. Ambas leem o valor 10. Ambas somam 1 e gravam 11. O programa perde um incremento. O erro não gera aviso nem segfault.

3. Balanceamento de carga

Testar se 4 é primo custa poucos ciclos. Testar se 4.999.999 é primo custa muitos ciclos. A carga de trabalho varia entre iterações.

O escalonamento static divide os índices em blocos contíguos iguais:

  • Thread 0: testa de 2 até 2.500.000.
  • Thread 1: testa de 2.500.001 até 5.000.000.

A Thread 1 processa números maiores e gasta mais ciclos. A Thread 0 termina antes e fica ociosa. Esse desequilíbrio reduz o speedup abaixo do ideal.

Questões adicionais

Questão adicional 1 de 2
Por que a contagem compartilhada produz race condition?
  1. A) Incrementos concorrentes podem perder atualizações entre threads
  2. B) Divisões inteiras sempre retornam resultados não determinísticos
  3. C) Laços paralelos ignoram automaticamente números primos pequenos
  4. D) Cada thread executa uma quantidade fixa diferente
Conferir resposta

Resposta: A. Incrementos concorrentes podem perder atualizações entre threads.

Questão adicional 2 de 2
Qual recurso combina contagens locais com baixo custo?
  1. A) Uma cláusula reduction aplicada ao contador compartilhado
  2. B) Uma região critical aplicada em toda divisão
  3. C) Uma barreira explícita depois de cada candidato
  4. D) Um lock diferente para cada possível divisor
Conferir resposta

Resposta: A. Uma cláusula reduction aplicada ao contador compartilhado.

1. Compilação e execução

# Compilação com OpenMP
$ gcc -std=c11 -Wall -Wextra -fopenmp tarefa05.c -o tarefa05 -lm

# Executa com o padrão de threads do sistema
$ ./tarefa05 5000000

# Define 4 threads e executa
$ export OMP_NUM_THREADS=4
$ ./tarefa05 5000000

# Executa definindo a variável inline
$ OMP_NUM_THREADS=2 ./tarefa05 5000000
  • O argumento é o limite superior $N$ para contagem de primos.
  • A saída mostra seq_time, par_time, seq_count e par_count.
  • Use ./execute.sh para rodar o experimento completo com todas as thread counts e gerar os gráficos.

2. Sintaxe básica

#pragma omp parallel for
for (long numero_atual = 0; numero_atual < limite_superior; numero_atual++) {
    // Operações independentes sobre o número atual
}
  • O laço precisa de limites fixos. O OpenMP calcula a divisão antes de executar.
  • Variáveis declaradas dentro do laço são privadas por padrão.

3. Escalonamento (schedule)

A cláusula schedule(tipo, tamanho_bloco) controla a divisão das iterações.

  • schedule(static) — Divide as iterações em blocos iguais no início. Custo mínimo. Ideal para carga uniforme.
  • schedule(dynamic, tamanho_bloco) — Cada thread requisita um bloco sob demanda. Mais overhead, mas equilibra carga desigual.

4. Race condition com variável compartilhada

long total_primos = 0;
#pragma omp parallel for
for (long numero_atual = 0; numero_atual < limite_superior; numero_atual++) {
    if (eh_primo(numero_atual)) total_primos++;  // Race condition: resultado incorreto
}

Múltiplas threads leem e escrevem total_primos ao mesmo tempo. O resultado fica corrompido.
