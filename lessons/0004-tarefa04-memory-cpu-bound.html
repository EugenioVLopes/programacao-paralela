Lição 04: Limites de Memória e CPU com OpenMP

Tarefa 04 • Dissecção de tarefa04.c • Saturação de barramento e poder de processamento

1. O problema

Programas paralelos encontram gargalos físicos diferentes. Aplicações limitadas por memória dependem da largura de banda do barramento. Aplicações limitadas por CPU dependem da velocidade das unidades aritméticas.

2. Dissecção de tarefa04.c

1. Teste limitado por memória (soma de vetores)

#pragma omp parallel for
for (long i = 0; i < total_elementos; ++i) {
    C[i] = A[i] + B[i];
}
  • O laço lê dois valores da memória e grava um resultado.
  • A intensidade aritmética é baixa: 1 operação para 24 bytes transferidos.
  • O barramento de memória satura com poucas threads. O ganho de desempenho estagna.

2. Teste limitado por processamento (cálculos intensivos)

#pragma omp parallel for
for (long i = 0; i < total_elementos; ++i) {
    double val = V[i];
    for (int j = 0; j < 50; ++j) {
        val = sqrt(val + j * 0.01) + sin(val);
    }
    V[i] = val;
}
  • O laço lê o valor uma única vez para o registrador local.
  • A CPU executa 50 iterações de funções matemáticas na ALU.
  • O resultado volta para a memória apenas no final.
  • A intensidade aritmética é alta. O desempenho escala de forma quase linear.

O que observar

  • Limitado por CPU: Cada núcleo físico traz unidades aritméticas próprias. O speedup cresce com mais threads.
  • Limitado por memória: Todos os núcleos compartilham o mesmo barramento. Adicionar threads não aumenta a largura de banda.

3. Quizzes

Questão 1 de 2
O que causa o gargalo de von Neumann em aplicações limitadas por memória?
Correto. As CPUs processam dados muito mais rápido do que o barramento consegue entregar da memória RAM, deixando os núcleos ociosos.
Questão 2 de 2
Por que o multithreading de hardware pode prejudicar o desempenho de códigos limitados por memória?
Correto. Com o barramento de memória já saturado, threads extras aumentam a fila de espera e a contenção no controlador de memória.
