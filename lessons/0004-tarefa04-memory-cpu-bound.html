Lição 04: Limites de Memória e CPU com OpenMP

Tarefa 04 • Dissecção de tarefa04.c • Saturação de barramento e poder de processamento

1. O problema

Programas paralelos encontram gargalos físicos diferentes. Aplicações limitadas por memória dependem da largura de banda do barramento. Aplicações limitadas por CPU dependem da velocidade das unidades aritméticas.

2. Dissecção de tarefa04.c

1. Teste limitado por memória (soma de vetores)

#pragma omp parallel for
for (long i = 0; i < total_elementos; ++i) {
    C[i] = A[i] + B[i];
}
  • O laço lê dois valores da memória e grava um resultado.
  • A intensidade aritmética é baixa: 1 operação para 24 bytes transferidos.
  • O barramento de memória satura com poucas threads. O ganho de desempenho estagna.

2. Teste limitado por processamento (cálculos intensivos)

#pragma omp parallel for
for (long i = 0; i < total_elementos; ++i) {
    double val = V[i];
    for (int j = 0; j < 50; ++j) {
        val = sqrt(val + j * 0.01) + sin(val);
    }
    V[i] = val;
}
  • O laço lê o valor uma única vez para o registrador local.
  • A CPU executa 50 iterações de funções matemáticas na ALU.
  • O resultado volta para a memória apenas no final.
  • A intensidade aritmética é alta. O desempenho escala de forma quase linear.

O que observar

  • Limitado por CPU: Cada núcleo físico traz unidades aritméticas próprias. O speedup cresce com mais threads.
  • Limitado por memória: Todos os núcleos compartilham o mesmo barramento. Adicionar threads não aumenta a largura de banda.

3. Quizzes

Questão 1 de 2
O que causa o gargalo de von Neumann em aplicações limitadas por memória?
Correto. As CPUs processam dados muito mais rápido do que o barramento consegue entregar da memória RAM, deixando os núcleos ociosos.
Questão 2 de 2
Por que o multithreading de hardware pode prejudicar o desempenho de códigos limitados por memória?
Correto. Com o barramento de memória já saturado, threads extras aumentam a fila de espera e a contenção no controlador de memória.

Fundamentação teórica

Teoria, modelagem matemática e contexto de HPC integrados à prática desta tarefa.

1. Gargalo de von Neumann

A arquitetura de von Neumann separa a unidade de processamento da memória principal. O barramento de comunicação possui largura de banda finita.

O poder de cálculo da CPU aumentou mais rápido que a velocidade da memória DRAM. Essa diferença cria o gargalo de von Neumann. A CPU passa ciclos ociosa esperando a chegada dos dados.

2. Intensidade aritmética

A intensidade aritmética mede as operações de ponto flutuante realizadas por byte transferido:

$$\text{IA} = \frac{\text{FLOPs}}{\text{Bytes Transferidos}}$$

Aplicações com baixa intensidade aritmética esgotam a largura de banda da memória. Aplicações com alta intensidade aritmética ocupam as unidades de cálculo da CPU.

3. Limitado por memória vs Limitado por processamento

  • Limitado por memória: O tempo total depende da taxa de transferência da memória RAM. As unidades aritméticas passam tempo ociosas.
  • Limitado por CPU: O tempo total depende da velocidade de execução das instruções na CPU. O acesso à memória é infrequente.

4. Efeitos do multithreading em hardware

O multithreading produz resultados opostos dependendo do perfil da carga de trabalho:

  • Em aplicações limitadas por CPU: Mais threads ocupam unidades aritméticas livres e aumentam a taxa de processamento. O speedup escala com os núcleos.
  • Em aplicações limitadas por memória: Mais threads disputam o mesmo barramento saturado. O tempo de execução estagna ou piora devido à contenção.

Questões adicionais

Questão adicional 1 de 2
Qual métrica separa cargas de memória e processamento?
  1. A) Operações realizadas efetivamente por cada byte transferido
  2. B) Threads criadas por cada processo executado agora
  3. C) Caches privadas por cada núcleo físico disponível
  4. D) Arquivos abertos por cada chamada do programa
Conferir resposta

Resposta: A. Operações realizadas por cada byte transferido.

  1. A) O recurso compartilhado atingiu sua vazão máxima
  2. B) O compilador removeu todas as instruções úteis
  3. C) O relógio monotônico alterou a frequência central
  4. D) O programa calculou um resultado numericamente exato
Conferir resposta

Resposta: A. O recurso compartilhado atingiu sua vazão máxima.

1. Controle de threads no terminal

A variável de ambiente OMP_NUM_THREADS define o total de threads da execução:

# Compilação padrão ativando OpenMP
$ gcc -std=c11 -Wall -Wextra -fopenmp programa.c -o programa -lm

# Define para 4 threads e executa
$ export OMP_NUM_THREADS=4
$ ./programa

# Executa definindo a variável inline
$ OMP_NUM_THREADS=2 ./programa

2. Divisão de laços com OpenMP

#pragma omp parallel for
for (long i = 0; i < total_elementos; ++i) {
    C[i] = A[i] + B[i];
}

Funções da biblioteca OpenMP

#include <omp.h>

int total_threads = omp_get_max_threads(); // Retorna o limite de threads
