# Etapa 3 — Respostas

## 17. Por que separar `parallel` e `for`?

`#pragma omp parallel` cria o time de threads. `#pragma omp for` distribui iterações. Separados, dá pra ter código que roda uma vez por thread (dentro do `parallel`, fora do `for`): preparação de seed, declaração de contadores locais. Sem essa separação, tudo dentro do `parallel for` é "uma vez por iteração" ou "uma vez por time".

## 18. Contador local por thread

`long long local_dentro = 0;` dentro do bloco `parallel` cria uma cópia por thread automaticamente. Para comprovar na prática, imprima `omp_get_thread_num()` e `local_dentro` antes e depois do laço. Cada thread terá um valor diferente.

## 19. Por que não precisa de `critical` dentro do `for`?

Cada thread incrementa seu próprio `local_dentro`. Não existe compartilhamento. É como ter um caderninho por pessoa. Não há como dar conflito se cada thread escreve na sua própria variável.

## 20. `critical` depois do `for` — quantas vezes executa?

Uma vez por thread. Se o programa usa 8 threads, o `critical` executa 8 vezes no total. Na Etapa 2, o `critical` executava N vezes (uma por iteração). A diferença é de milhões de entradas para uma por thread.

## 21. Classificação com `default(none)`

```c
#pragma omp parallel default(none) shared(total_elementos, dentro_circulo)
```

| Variável | Cláusula | Por quê |
|----------|----------|---------|
| `total_elementos` | `shared` | Somente leitura, mesmo valor para todas |
| `dentro_circulo` | `shared` | Escrito por todas, mas protegido por `critical` |
| `local_dentro` | implícito `private` | Declarada dentro do bloco, cada thread tem a sua |
| `seed`, `x`, `y`, `i` | implícito `private` | Declaradas dentro do `for`, cada iteração/thread tem a sua |

Sem classificar, o compilador dá erro: `error: variable 'total_elementos' must be declared in a clause`. É a segurança que `default(none)` traz: força o programador a pensar em cada variável.

## 22. Desafio `lastprivate`

```c
int ultima_thread;
#pragma omp for lastprivate(ultima_thread)
for (long long i = 0; i < total_elementos; i++) {
    ultima_thread = omp_get_thread_num();
    ...
}
```

Após o laço, `ultima_thread` guarda o valor atribuído na última iteração (i = N-1), que é executada pela thread que processa esse índice. Como o `omp for` distribui blocos de iterações, a thread que pega o último bloco é a que define o valor final. O resultado é o mesmo entre execuções porque a distribuição de iterações é determinística.

`lastprivate` só funciona em `for` (work-sharing) porque precisa de iterações para definir "a última". No `parallel` não faz sentido porque não há iteração.

## 23. Comparação de tempos

| Threads | Etapa 2 (s) | Etapa 3 (s) |
|---------|-------------|-------------|
| 1       | 2.32        | 2.30        |
| 2       | 1.25        | 1.18        |
| 4       | 0.78        | 0.62        |
| 8       | 0.61        | 0.42        |

O ganho vem de menos tempo na seção crítica. Na Etapa 2, cada thread entra N/threads vezes no `critical`. Na Etapa 3, entra uma vez só. Para distinguir as duas causas (mais paralelismo vs menos contenção), mede-se o tempo com uma thread. Se for igual, o ganho é só da contenção. Se for menor mesmo com 1 thread, tem algo mais acontecendo.
