# Etapa 2 — Respostas

## 13-14. Por que `critical` envolve só o incremento?

O `#pragma omp critical` bloqueia a execução para todas as threads. Só uma thread entra por vez. Se envolvesse o laço inteiro, as threads executariam em série, como se fosse sequencial. O paralelismo seria zero. Envolvendo só `dentro_circulo++`, as threads fazem o trabalho pesado (sorteio, cálculo) em paralelo e só sincronizam no incremento.

## 15. Confirmação de determinismo

```bash
for i in 1 2 3 4 5; do ./e2; done
```

O valor de π é sempre o mesmo entre execuções. O `critical` garante que os increments não se perdam.

## 16. Tabela de tempos

| Threads | Tempo (s) |
|---------|-----------|
| 1       | 2.32      |
| 2       | 1.25      |
| 4       | 0.78      |
| 8       | 0.61      |

O tempo melhora com mais threads, mas não é proporcional. Cada thread entra no `critical` ~N/threads vezes. Com 8 threads, são milhões de entradas na seção crítica, e cada uma tem custo de sincronização (travamento de mutex). O `critical` vira gargalo.

```bash
OMP_NUM_THREADS=1 ./e2
OMP_NUM_THREADS=2 ./e2
OMP_NUM_THREADS=4 ./e2
OMP_NUM_THREADS=8 ./e2
```

Tempos aproximados (variam por máquina).
