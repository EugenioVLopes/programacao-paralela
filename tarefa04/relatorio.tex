\section{Enunciado}
Implementar dois programas paralelos em C com OpenMP: um limitado por memória (somas simples em vetores) e outro limitado por CPU (cálculos matemáticos intensivos iterativos locais). Paralelizar ambos com \texttt{\#pragma omp parallel for} e medir o tempo de execução variando o número de threads. Analisar quando o desempenho melhora, estabiliza ou piora, refletindo sobre como o multithreading de hardware pode ajudar em programas \textit{cpu-bound}, mas atrapalhar em programas \textit{memory-bound} devido à competição por recursos.

\section{Fundamentação teórica}

\subsection{O gargalo de von Neumann}
A arquitetura de von Neumann clássica separa a memória principal da unidade de processamento. Para que a CPU calcule algo, ela precisa buscar dados na RAM através do barramento do sistema. Com a evolução do hardware, os núcleos das CPUs tornaram-se capazes de realizar operações lógicas e aritméticas em uma taxa absurdamente mais alta do que a taxa de transferência suportada pelo barramento de memória (largura de banda máxima). Essa disparidade de velocidade gera o \textbf{gargalo de von Neumann}, também chamado de \textit{Memory Wall}.

\subsection{Intensidade aritmética e limites de escalabilidade}
A classificação de um algoritmo como \textit{memory-bound} (limitado por memória) ou \textit{cpu-bound} (limitado por processamento) depende de sua intensidade aritmética: a razão entre as operações aritméticas executadas e os bytes transferidos.

Em um cenário \textit{memory-bound}, a intensidade aritmética é muito baixa. Por exemplo, a soma de dois vetores $C[i] = A[i] + B[i]$ realiza uma operação (\texttt{ADD}) para três acessos à memória (leitura de $A$, leitura de $B$, e gravação em $C$). A CPU processa essa soma instantaneamente e passa a maior parte do tempo ociosa, esperando a RAM. 

Em um cenário \textit{cpu-bound}, a intensidade aritmética é alta. Um dado é carregado da memória (ou reside diretamente nos registradores e no cache L1) e sofre uma série de cálculos pesados sequenciais (ex.: séries de Taylor, raiz quadrada, trigonometria). O limitante passa a ser a capacidade da Unidade Lógica e Aritmética (ALU).

\subsection{O efeito do Simultaneous Multithreading (SMT)}
CPUs modernas apresentam núcleos lógicos extras usando SMT (\textit{Hyper-threading} na Intel). Isso significa que um único núcleo físico gerencia duas linhas de execução concorrentes. Em programas \textit{cpu-bound}, isso ajuda, pois quando uma thread sofre latência de pipeline, a segunda mantém a ALU ocupada. Porém, em programas \textit{memory-bound}, as duas threads lógicas começam a disputar o mesmo barramento saturado e a mesma cache L1, frequentemente piorando o tempo total de resposta por contenção (\textit{thrashing}).

\section{Experimento}

\subsection{Configuração}
O código utiliza $N=50.000.000$ de elementos. Foram alocados quatro vetores do tipo \texttt{double}: três para o teste \textit{memory-bound} e um para o teste \textit{cpu-bound}. 

No teste \textit{memory-bound}, a iteração calcula uma simples soma de vetores, forçando leituras e escritas sem reuso temporal no nível da cache, estressando a capacidade de leitura sequencial da RAM.

No teste \textit{cpu-bound}, itera-se sobre um único vetor. Cada elemento é carregado para uma variável local (\texttt{double val}), submetido a 50 iterações computacionais pesadas de funções trigonométricas (\texttt{sin}) e radiciação (\texttt{sqrt}), e só então o valor consolidado é salvo de volta na memória, minimizando os acessos ao barramento.

As medições foram feitas utilizando \texttt{clock\_gettime(CLOCK\_MONOTONIC)} e a compilação foi gerada via GCC (sinalizador \texttt{-O3} e \texttt{-fopenmp}). O número de threads foi variado externamente pelo script de execução utilizando a variável de ambiente \texttt{OMP\_NUM\_THREADS}.

\section{Código-fonte}

\begin{lstlisting}[caption={tarefa04.c}]
#define _POSIX_C_SOURCE 199309L

#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <math.h>
#include <omp.h>

#define DEFAULT_N 50000000L

static double agora(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}

int main(int argc, char **argv) {
    long n = argc > 1 ? atol(argv[1]) : DEFAULT_N;
    if (n <= 0) {
        fprintf(stderr, "Uso: %s [numero]\n", argv[0]);
        return 1;
    }

    double *A = malloc((size_t)n * sizeof(*A));
    double *B = malloc((size_t)n * sizeof(*B));
    double *C = malloc((size_t)n * sizeof(*C));
    double *V = malloc((size_t)n * sizeof(*V));

    if (!A || !B || !C || !V) return 1;

    for (long i = 0; i < n; ++i) {
        A[i] = i * 0.5; B[i] = i * 0.25; V[i] = i * 0.1;
    }

    int n_threads = omp_get_max_threads();

    double inicio_mem = agora();
    #pragma omp parallel for
    for (long i = 0; i < n; ++i) {
        C[i] = A[i] + B[i];
    }
    double tempo_mem = agora() - inicio_mem;

    double inicio_cpu = agora();
    #pragma omp parallel for
    for (long i = 0; i < n; ++i) {
        double val = V[i];
        for (int j = 0; j < 50; ++j) {
            val = sqrt(val + j * 0.01) + sin(val);
        }
        V[i] = val;
    }
    double tempo_cpu = agora() - inicio_cpu;

    printf("N=%ld threads=%d memory_bound=%.9f cpu_bound=%.9f\n", 
           n, n_threads, tempo_mem, tempo_cpu);

    double soma_check = C[n/2] + V[n/2];
    if (soma_check == 0.0) printf(" \n");

    free(A); free(B); free(C); free(V);
    return 0;
}
\end{lstlisting}

\section{Discussão}

\subsection{Escalabilidade e limitação da memória}
Os dados empíricos atestam nitidamente que o escalonamento sofre de patologias dependentes da intensidade aritmética. Para a tarefa \textit{cpu-bound}, a curva de aceleração sobe progressivamente e mantém-se relativamente próxima do limite ideal. Quando atingimos o total de 14 núcleos físicos da máquina, o speedup já marca 7$\times$, com a capacidade da CPU de ponto flutuante dividindo de forma razoavelmente consistente a carga de trabalho.

Já a tarefa \textit{memory-bound}, que simplesmente soma vetores, apresenta um rápido platô. Após cerca de 4 threads, a velocidade estaciona em valores marginais (próximos de 0,01 s). Adicionar 8, 14 ou 28 threads não melhora substancialmente o desempenho. Isso comprova o gargalo de von Neumann: a máquina chegou ao limite de quantos gigabytes por segundo consegue despachar através da hierarquia de memória para alimentar as unidades lógicas; as ALUs estão esfomeadas (\textit{data starvation}) aguardando a latência de memória.

\subsection{Regressão de desempenho por SMT (Hyper-threading)}
Fica muito claro na tabela, no salto entre os núcleos físicos e lógicos (até a thread 28), que o multithreading de hardware pode ser prejudicial para operações limitadas por memória. Ao sobrecarregar a fila de acesso à RAM com ainda mais requisições concorrentes disparadas por threads lógicas (threads 15 a 28) compartilhando o mesmo núcleo físico e cache L1 das físicas, a contenção do barramento se exacerba. 

Como visto na tabela, o tempo do \textit{memory-bound} com 28 threads ativas sofreu regressão (0,015 s, um speedup de 5,20$\times$), sendo consideravelmente mais lento do que quando rodou em apenas 14 ou 8 threads (0,009 s e 0,011 s). No modelo \textit{cpu-bound}, o SMT proveu vantagens secundárias e ajudou o speedup a alcançar cerca de 8,91$\times$.

\section{Conclusão}

A alocação massiva de \textit{threads} não soluciona restrições estruturais de velocidade. O programador precisa classificar a intensidade aritmética do seu algoritmo: caso a aplicação seja intensiva em memória, as otimizações necessárias devem focar em padronizar o acesso aos dados para otimizar as linhas de cache e minimizar os \textit{cache misses}, em vez de cegamente empregar mais \textit{threads} simultâneas. O \texttt{\#pragma omp parallel for} escala de forma ideal apenas para lógicas onde os dados necessários se mantêm temporalmente nos registradores por múltiplos ciclos da ALU.
