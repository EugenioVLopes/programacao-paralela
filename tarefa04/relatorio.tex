\section{Enunciado}
Implementar dois programas paralelos em C com OpenMP: um limitado por memória (somas simples em vetores) e outro limitado por CPU (cálculos matemáticos intensivos iterativos locais). Paralelizar ambos com \texttt{\#pragma omp parallel for} e medir o tempo de execução variando o número de threads. Analisar quando o desempenho melhora, estabiliza ou piora, refletindo sobre como o multithreading de hardware pode ajudar em programas \textit{cpu-bound}, mas atrapalhar em programas \textit{memory-bound} devido à competição por recursos.

\section{Fundamentação teórica}

\subsection{O gargalo de von Neumann}
A arquitetura de von Neumann separa a memória principal da unidade de processamento. A CPU busca dados na RAM pelo barramento do sistema. Com a evolução do hardware, os núcleos passaram a executar operações aritméticas ordens de grandeza mais rápido do que o barramento consegue entregar dados. Em um processador moderno, a ALU pode consumir centenas de GFLOP/s, enquanto a largura de banda da memória não passa de dezenas de GB/s. Essa disparidade é o \textbf{gargalo de von Neumann}, ou \textit{Memory Wall}.

\subsection{Intensidade aritmética e limites de escalabilidade}
A intensidade aritmética é a razão entre operações aritméticas executadas e bytes transferidos da memória. Esse número classifica o algoritmo como \textit{memory-bound} ou \textit{cpu-bound}.

Um algoritmo \textit{memory-bound} tem intensidade aritmética baixa. A soma de vetores $C[i] = A[i] + B[i]$ executa 1 operação para 24 bytes transferidos (2 leituras + 1 escrita de \texttt{double}). A CPU termina a soma em poucos ciclos e fica ociosa esperando o próximo dado chegar da RAM.

Um algoritmo \textit{cpu-bound} tem intensidade aritmética alta. O dado é carregado uma vez e passa por muitas operações antes de voltar à memória. Séries de Taylor, raiz quadrada e trigonometria são exemplos. O limitante é a capacidade da ALU, não a largura de banda.

\subsection{O efeito do Simultaneous Multithreading (SMT)}
CPUs modernas expõem núcleos lógicos extras via SMT (\textit{Hyper-threading} na Intel). Um único núcleo físico gerencia duas threads. Em código \textit{cpu-bound}, a segunda thread aproveita ciclos ociosos do pipeline e mantém a ALU ocupada. Em código \textit{memory-bound}, o efeito é o oposto: as duas threads disputam o mesmo barramento já saturado e a mesma cache L1, aumentando a contenção e piorando o tempo total.

\section{Experimento}

\subsection{Configuração}
O programa aloca quatro vetores de \texttt{double} com $N = 50.000.000$ elementos: três para o teste \textit{memory-bound} (A, B, C) e um para o teste \textit{cpu-bound} (V).

O teste \textit{memory-bound} calcula $C[i] = A[i] + B[i]$. O laço lê dois vetores e escreve um terceiro, sem reuso temporal de cache. Toda a pressão recai sobre a largura de banda da RAM.

O teste \textit{cpu-bound} carrega cada \texttt{V[i]} para uma variável local e aplica 50 iterações de \texttt{sqrt} e \texttt{sin}. Só ao final das 50 iterações o resultado volta à memória. O acesso à RAM é mínimo; o gargalo é a ALU.

O programa mede o tempo com \texttt{clock\_gettime(CLOCK\_MONOTONIC)}. O GCC compilou o código com \texttt{-O3} e \texttt{-fopenmp}. Um script externo variou \texttt{OMP\_NUM\_THREADS} de 1 a 28.

\section{Código-fonte}

\begin{lstlisting}[caption={tarefa04.c}]
#define _POSIX_C_SOURCE 199309L

#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <math.h>
#include <omp.h>

#define DEFAULT_N 50000000L

static double agora(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}

int main(int argc, char **argv) {
    long n = argc > 1 ? atol(argv[1]) : DEFAULT_N;
    if (n <= 0) {
        fprintf(stderr, "Uso: %s [numero]\n", argv[0]);
        return 1;
    }

    double *A = malloc((size_t)n * sizeof(*A));
    double *B = malloc((size_t)n * sizeof(*B));
    double *C = malloc((size_t)n * sizeof(*C));
    double *V = malloc((size_t)n * sizeof(*V));

    if (!A || !B || !C || !V) return 1;

    for (long i = 0; i < n; ++i) {
        A[i] = i * 0.5; B[i] = i * 0.25; V[i] = i * 0.1;
    }

    int n_threads = omp_get_max_threads();

    double inicio_mem = agora();
    #pragma omp parallel for
    for (long i = 0; i < n; ++i) {
        C[i] = A[i] + B[i];
    }
    double tempo_mem = agora() - inicio_mem;

    double inicio_cpu = agora();
    #pragma omp parallel for
    for (long i = 0; i < n; ++i) {
        double val = V[i];
        for (int j = 0; j < 50; ++j) {
            val = sqrt(val + j * 0.01) + sin(val);
        }
        V[i] = val;
    }
    double tempo_cpu = agora() - inicio_cpu;

    printf("N=%ld threads=%d memory_bound=%.9f cpu_bound=%.9f\n", 
           n, n_threads, tempo_mem, tempo_cpu);

    double soma_check = C[n/2] + V[n/2];
    if (soma_check == 0.0) printf(" \n");

    free(A); free(B); free(C); free(V);
    return 0;
}
\end{lstlisting}

A \textbf{intensidade aritmética} (AI) de cada kernel foi calculada como:

\begin{itemize}
    \item \textbf{Memory-bound} ($C[i] = A[i] + B[i]$): 1 FLOP por elemento, com 3 acessos de 8 bytes (2 leituras + 1 escrita = 24 bytes). Portanto $\text{AI} = 1/24 \approx 0{,}042$ FLOP/byte.
    \item \textbf{CPU-bound} (50 iterações de \texttt{sqrt} + \texttt{sin}): aproximadamente 1050 FLOPs por elemento (50 $\times$ 21 FLOPs/iteração), com apenas 16 bytes transferidos (1 leitura + 1 escrita). Portanto $\text{AI} = 1050/16 \approx 65{,}6$ FLOP/byte.
\end{itemize}

Os pontos do kernel \textit{memory-bound} ficam à esquerda do ponto de crista (AI $\approx 6{,}4$), na região inclinada do roofline, onde a largura de banda limita o desempenho. Os pontos do kernel \textit{cpu-bound} ficam à direita, na região plana, limitados pelo pico computacional.

\section{Discussão}

\subsection{Escalabilidade e limitação da memória}
A escalabilidade dos dois kernels diverge porque o recurso disputado é diferente. No kernel \textit{cpu-bound}, cada núcleo traz sua própria ALU. Dobrar os núcleos dobra a capacidade de processamento disponível, e o speedup acompanha a curva ideal enquanto houver núcleos físicos livres.

No kernel \textit{memory-bound}, todos os núcleos compartilham o mesmo barramento de memória. A partir do momento em que o barramento atinge sua vazão máxima, núcleos extras ficam ociosos esperando dados. O tempo estabiliza independentemente de quantas threads sejam criadas. O gráfico de tempo de execução (Figura~\ref{fig:speedup}) mostra essa estagnação com clareza.

\subsection{Interpretação do Roofline Model}
O Roofline Model (Figura~\ref{fig:roofline}) explica essa diferença de forma estrutural. Cada kernel ocupa uma posição fixa no eixo horizontal, determinada pela sua intensidade aritmética. O teto de desempenho nessa posição define o máximo que o hardware pode entregar.

O kernel \textit{memory-bound} tem AI tão baixa que fica na rampa inclinada do gráfico, limitado pela largura de banda. Nessa região, adicionar mais poder de processamento não adianta: o gargalo é a velocidade com que os dados chegam da RAM. Para melhorar, seria preciso mudar o algoritmo para reutilizar dados em cache.

O kernel \textit{cpu-bound} tem AI alta o suficiente para ficar na região plana, limitado pela capacidade das ALUs. Aqui, mais núcleos significa mais capacidade real, e o paralelismo funciona.

\subsection{Regressão de desempenho por SMT (Hyper-threading)}
O SMT permite que dois fluxos de execução compartilhem o mesmo núcleo físico. Em código \textit{cpu-bound}, a segunda thread ocupa ciclos que a primeira desperdiça com latência de pipeline, e o desempenho melhora. Em código \textit{memory-bound}, ambas as threads geram requisições ao mesmo barramento já saturado. O resultado é contenção: as requisições se enfileiram, e o tempo piora em vez de melhorar.

Os dados confirmam esse comportamento. Acima de 14 threads, o kernel \textit{memory-bound} regride enquanto o \textit{cpu-bound} ainda extrai ganho marginal do SMT.

\section{Conclusão}

Adicionar threads não resolve gargalos de largura de banda. Neste experimento, o kernel \textit{memory-bound} parou de escalar com 4 threads e piorou com 28. O kernel \textit{cpu-bound} escalou até 8,91$\times$ com 28 threads. A diferença é a intensidade aritmética: 0,042 contra 65,6 FLOP/byte.

Antes de paralelizar com \texttt{\#pragma omp parallel for}, vale identificar o gargalo. Se for largura de banda, o caminho é melhorar o padrão de acesso à memória e aumentar o reuso de cache. Se for capacidade de processamento, mais threads resolvem.
