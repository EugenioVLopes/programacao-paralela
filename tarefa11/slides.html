O PROBLEMA

O modelo considera só a viscosidade

∂u/∂t = ν∇²u

O que evolui

Um campo de velocidade em uma malha bidimensional. A viscosidade espalha variações locais ao longo do tempo.

Escopo do cálculo

Pressão, advecção e forças externas ficam de fora. A simulação é o caso viscoso do enunciado, não um solver completo de Navier–Stokes.

ESTADO DO CÁLCULO

Um passo lê u e escreve v

u · passo n

Fonte de todos os valores do stencil deste passo. Nenhuma célula de u muda durante a varredura.

v · passo n + 1

Destino das células atualizadas. Cada posição interna tem um único escritor.

v[i * N + j] = u[i * N + j] + r *
  (u[(i - 1) * N + j] + u[(i + 1) * N + j] +
   u[i * N + j - 1] + u[i * N + j + 1] -
   4.0 * u[i * N + j]);
Depois do passo, trocar os ponteiros evita copiar a malha inteira.

DEPENDÊNCIAS

As células são independentes dentro do passo

Leitura comum

Várias threads consultam u. Nenhuma escreve nele durante a varredura.

Saídas distintas

Cada par (i,j) grava uma posição diferente de v.

RAW entre passos

O próximo passo precisa ler as saídas já concluídas do passo atual.

passo n → todas as células internas → passo n + 1

O espaço da malha pode ser repartido. A sequência temporal precisa continuar ordenada.

ESTRUTURA COMUM

Distribuir o laço espacial; sincronizar cada passo

#pragma omp parallel
{
  for (int t = 0; t < num_passos; ++t) {
    #pragma omp for schedule(...)
    for (int i = 1; i < N - 1; ++i)
      for (int j = 1; j < N - 1; ++j)
        atualizar(u, v, i, j);

    #pragma omp single
    trocar_ponteiros(&u, &v);
  }
}

Barreira de omp for

As threads terminam todas as células antes que o campo atual seja trocado.

Single e sua barreira

Uma thread troca u e v; a barreira implícita mantém todas as threads no mesmo passo.

SCHEDULE

O escalonador decide quem recebe cada chunk

static

Reparte as iterações antes do laço. A thread mantém sua parcela sem solicitar novos chunks.

dynamic, 16

Entrega chunks de 16 iterações sob demanda. Quem termina pede outro ao escalonador.

guided, 16

Começa com chunks maiores, reduz o tamanho ao longo do laço e respeita 16 como mínimo.

Mais redistribuição pode equilibrar carga variável; também pode aumentar a coordenação.

Nesta malha, cada célula executa o mesmo stencil. A carga por célula é uniforme.

dynamic

Chunks do mesmo tamanho são requisitados conforme cada thread termina. Útil quando o custo das iterações varia.

DCA3703 · Tarefa 1110 / 19
COLLAPSE(2)

Combinar laços muda o tamanho real do chunk

Sem collapse

16 linhas

Com schedule(dynamic,16), cada iteração do laço externo é uma linha de 510 células.

16 × 510 = 8.160 células

Com collapse(2)

16 células

Os dois laços formam um único espaço; cada iteração lógica é uma célula.

16 iterações = 16 células

#pragma omp for schedule(dynamic, 16)
/* chunk: 16 linhas */

#pragma omp for collapse(2) schedule(dynamic, 16)
/* chunk: 16 células */

O valor 16 é contado nas iterações do espaço distribuído, não em bytes nem em operações aritméticas.
