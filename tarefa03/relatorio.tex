\section{Enunciado}
Implementar três laços em C para investigar ILP: inicializar um vetor com um
cálculo simples, somar seus elementos com dependência entre iterações e repetir
a soma com múltiplos acumuladores. Comparar versões compiladas com \texttt{-O0},
\texttt{-O2} e \texttt{-O3}, analisando o efeito do estilo do código e das
dependências no desempenho.

\section{Fundamentação teórica}

\subsection{O que é ILP}
Uma CPU superescalar consegue iniciar mais de uma instrução por ciclo, desde que
elas não dependam umas das outras. Essa sobreposição se chama paralelismo em
nível de instrução (ILP). O limite prático vem das dependências de dados: se a
instrução~B precisa do resultado da instrução~A, o processador espera A terminar
antes de começar B.

\subsection{Latência, throughput e por que acumuladores importam}
Uma soma inteira (\texttt{ADD}) em processadores x86 modernos tem latência de
1~ciclo e throughput de 1~operação por ciclo por porta. Quando o laço usa um
acumulador único, cada soma depende do resultado da soma anterior:
\(s_{i+1}=s_i+v[i+1]\). Isso cria uma cadeia de $N$ somas sequenciais, onde
cada uma espera 1~ciclo pela anterior. O processador tem capacidade de emitir
várias somas por ciclo, mas a dependência impede.

Com quatro acumuladores independentes (\texttt{s0}, \texttt{s1}, \texttt{s2},
\texttt{s3}), cada cadeia tem $N/4$ somas. As quatro cadeias não dependem entre
si, então o processador pode emitir somas de cadeias diferentes no mesmo ciclo.
O caminho crítico cai de $N$ para $N/4$ ciclos, um speedup teórico de até 4$\times$.

\subsection{O laço de inicialização}
O laço \texttt{v[i] = 3*i + 1} escreve posições diferentes do vetor a cada
iteração. Não há dependência entre escritas consecutivas, então o compilador
pode vetorizar o laço com instruções SIMD e o processador pode executar várias
escrituras em paralelo.

\section{Experimento}

\subsection{Configuração}
O vetor contém $N=100.000.000$ inteiros (\texttt{int}, 4~bytes cada), totalizando
aproximadamente 381,5~MiB (400~MB). Esse valor foi dimensionado com base na
arquitetura de teste (processador Intel Core i7-14700HX):
(1)~supera em mais de 11$\times$ o cache L3 compartilhado de 33~MiB (e os caches
L1D de 48~KiB e L2 de 2~MiB por núcleo), garantindo que o experimento
atravesse toda a hierarquia de memória até a DRAM;
(2)~mantém os tempos de execução na faixa de 26 a 300~ms, minimizando o peso
relativo do ruído de medição e do escalonador do sistema operacional; e
(3)~consome apenas uma fração da memória RAM principal, sem risco de
paginação em disco (\textit{swap}).

A função \texttt{v[i] = 3*i + 1} preenche o vetor. Depois, dois laços
somam todos os elementos: o primeiro com um acumulador, o segundo com quatro.

Cada laço é cronometrado isoladamente com
\texttt{clock\_gettime(CLOCK\_MONOTONIC)}, que tem resolução de nanossegundos e
não conta tempo de outros processos. O programa compara os dois resultados para
garantir que a soma com múltiplos acumuladores produz o mesmo valor.

\subsection{Compilação}
O código foi compilado três vezes, variando apenas o nível de otimização:
\begin{lstlisting}[language=bash]
gcc -std=c11 -Wall -Wextra -O0 tarefa03.c -o tarefa03_O0
gcc -std=c11 -Wall -Wextra -O2 tarefa03.c -o tarefa03_O2
gcc -std=c11 -Wall -Wextra -O3 tarefa03.c -o tarefa03_O3
\end{lstlisting}

\texttt{-O0} desliga todas as otimizações do compilador, o que preserva a
estrutura original do código. \texttt{-O2} aplica desenrolamento de laços e
alocação de registradores. \texttt{-O3} adiciona vetorização automática com
instruções SIMD.

\section{Código-fonte}
\begin{lstlisting}[caption={tarefa03.c}]
#define _POSIX_C_SOURCE 199309L

#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define DEFAULT_N 100000000L

static double agora(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}

int main(int argc, char **argv) {
    long n = argc > 1 ? atol(argv[1]) : DEFAULT_N;
    if (n <= 0) {
        fprintf(stderr, "Uso: %s [numero_de_elementos]\n", argv[0]);
        return 1;
    }

    int *v = malloc((size_t)n * sizeof(*v));
    if (!v) {
        perror("malloc");
        return 1;
    }

    double inicio = agora();
    for (long i = 0; i < n; ++i)
        v[i] = (int)(3 * i + 1);
    double tempo_inicializacao = agora() - inicio;

    inicio = agora();
    long long soma_dependente = 0;
    for (long i = 0; i < n; ++i)
        soma_dependente += v[i];
    double tempo_dependente = agora() - inicio;

    inicio = agora();
    long long s0 = 0, s1 = 0, s2 = 0, s3 = 0;
    long i = 0;
    for (; i + 3 < n; i += 4) {
        s0 += v[i];
        s1 += v[i + 1];
        s2 += v[i + 2];
        s3 += v[i + 3];
    }
    for (; i < n; ++i)
        s0 += v[i];
    long long soma_multiplos = s0 + s1 + s2 + s3;
    double tempo_multiplos = agora() - inicio;

    printf("N=%ld inicializacao=%.9f dependente=%.9f multiplos=%.9f "
           "somas=%lld,%lld\n", n, tempo_inicializacao,
           tempo_dependente, tempo_multiplos, soma_dependente,
           soma_multiplos);
    free(v);
    return soma_dependente != soma_multiplos;
}
\end{lstlisting}

\subsection{Leitura dos resultados}

Com \texttt{-O0}, a soma com quatro acumuladores rodou em 0,058~s contra
0,151~s do acumulador único: ganho de 2,58$\times$ de desempenho. O limite
teórico de aceleração seria de 4$\times$ (quatro cadeias independentes de cálculo).
Esse teto não é integralmente atingido porque a taxa de leitura da memória
(\texttt{load} de cada elemento do vetor) também impõe um piso ao tempo total
de processamento.

Com \texttt{-O2}, o compilador aplica desenrolamento de laço e alocação agressiva
de registradores na versão com acumulador único. O ganho da intervenção manual
cai para 1,08$\times$, pois o compilador reestrutura o fluxo de instruções
automaticamente.

Com \texttt{-O3}, os tempos de soma dependente (0,026~s) e de múltiplos acumuladores
(0,030~s) tornam-se equivalentes, com variação residual na ordem de 4~ms.
Nesse nível de otimização, a vetorização automática SIMD e a reordenação profunda
atuam em ambas as abordagens, fazendo com que o gargalo de execução seja dominado
pela taxa de transferência de dados da memória e não pela dependência aritmética
original.

A inicialização reduziu de 0,301~s em \texttt{-O0} para cerca de 0,102~s em
\texttt{-O2}. Como o laço de inicialização grava elementos contíguos em posições
independentes de memória, o compilador consegue aplicar vetorização SIMD com
amplo aproveitamento de largura de banda.

\section{Discussão}

\subsection{Caminho crítico e dependências de dados}
Os laços de soma executam o mesmo número de operações aritméticas, $O(N)$, porém
com caminhos críticos distintos. No acumulador único, cada iteração depende do
resultado imediato da anterior ($s_{i+1} = s_i + v[i+1]$), criando uma cadeia
estritamente sequencial de $N$ somas que impede a sobreposição de instruções.

Com quatro acumuladores, as operações são distribuídas em quatro cadeias
mutuamente independentes de comprimento $N/4$. Isso permite que a arquitetura
superescalar despache múltiplas instruções de adição por ciclo de clock. A soma
final dos acumuladores parciais (\texttt{s0 + s1 + s2 + s3}) requer apenas
três adições adicionais, custo irrelevante para $N = 10^8$.

\subsection{Atuação das otimizações do compilador}
Nos níveis \texttt{-O2} e \texttt{-O3}, o compilador aplica técnicas avançadas
de reordenação, desenrolamento de laços e vetorização vetorial SIMD. Esse processo
elimina a desvantagem do código sequencial direto, equiparando o desempenho da
versão ingênua ao da versão manualmente desenrolada.

\subsection{Escopo do paralelismo investigado}
O paralelismo analisado ocorre exclusivamente em nível de instrução (ILP) dentro
de um único núcleo de execução da CPU, por meio de unidades funcionais paralelas
e pipelines superescalares. Esse mecanismo opera internamente no hardware e não
deve ser confundido com paralelismo entre threads ou múltiplos núcleos físicos.

\section{Conclusão}
O experimento comprovou que dependências de dados entre iterações consecutivas
restringem diretamente a capacidade de execução paralela do pipeline. Sem
otimização do compilador (\texttt{-O0}), a divisão em quatro acumuladores
independentes proporcionou um ganho de $2,58\times$ na soma do vetor.

Com níveis de otimização elevados (\texttt{-O2} e \texttt{-O3}), o compilador
foi capaz de identificar e explorar automaticamente esse paralelismo, tornando
equivalente o desempenho de ambas as implementações. Assim, comprova-se que a
exposição de instruções independentes é essencial para o desempenho quando o
código depende da estrutura direta dada pelo programador.
