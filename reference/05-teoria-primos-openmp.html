Teoria: Paralelismo de Laços e Condições de Corrida

OpenMP • Paralelismo de Dados • Race Conditions • Redução

1. Introdução ao Paralelismo de Laços (Loop-Level Parallelism)

Muitos códigos passam a maior parte do tempo em laços. O padrão do OpenMP para acelerar esse processo é dividir as iterações entre as threads disponíveis.

O #pragma omp parallel for cria as threads e corta o laço. Se o código tem 1000 iterações e usa 4 threads, o escalonamento estático manda 250 iterações para cada thread logo no início.

2. O Problema: Race Conditions (Condições de Corrida)

Uma Race Condition acontece quando threads escrevem na mesma memória sem regras. O hardware sobrepõe as operações e o resultado quebra.

A CPU não processa count++ em um só passo. Ela executa três:

  1. LOAD: Lê o valor atual da memória para o registrador.
  2. ADD: Soma 1 no registrador.
  3. STORE: Salva o valor na memória.

Se a Thread A e a Thread B executam o LOAD no mesmo ciclo, ambas leem 10. Ambas somam e salvam 11. O programa perde um incremento.

3. A Solução: Cláusula de Redução (Reduction)

A cláusula reduction(operador:variável) resolve o problema sem travar as threads.

Como funciona nos bastidores:

  1. O compilador cria uma cópia local da variável para cada thread, com valor zero.
  2. Cada thread incrementa a própria cópia. Não há disputa de barramento nem espera.
  3. No fim do laço, o OpenMP soma os resultados locais na variável global.

4. Balanceamento de Carga (Load Balancing) e o caso dos Primos

Testar se 4 é primo custa pouco: falha na primeira divisão. Testar se 4.999.999 é primo gasta muitos laços.

Se o OpenMP divide os números com o static padrão:
Thread 1: Testa de 2 até 2.500.000
Thread 2: Testa de 2.500.001 até 5.000.000

A Thread 2 processa os maiores números e gasta mais ciclos de CPU. A Thread 1 termina cedo e fica ociosa. Esse desequilíbrio é o desbalanceamento de carga (Load Imbalance), e ele corta a escalabilidade do código.
