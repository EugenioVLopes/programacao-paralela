Teoria 06: Task OpenMP — Processamento de Lista com Tarefas

Processamento de lista encadeada com #pragma omp task • Agendamento de tarefas • Garantia de execuções únicas

1. Motivação: Por que task para listas?

As diretivas parallel for e parallel sections exigem que o paralelismo seja conhecido em tempo de compilação. O OpenMP divide os índices do laço entre as threads antes da execução começar. Isso funciona bem para iterações de laço, mas listas encadeadas não são arranjos contíguos: o compilador não sabe quantos nós existem até o programa percorrer a lista em tempo de execução.

A diretiva #pragma omp task resolve esse problema ao criar tarefas explícitas em tempo de execução. Cada nó da lista gera uma tarefa; o sistema de tarefas do OpenMP — não o programador — decide qual thread executa qual tarefa.

Ideia central: O task separa a criação da execução. Você gera todas as tarefas primeiro; o task runtime as distribui entre as threads disponíveis.

2. Anatomia de uma #pragma omp task

#pragma omp task [clause [, clause]...]
// código da tarefa — pode ser um bloco ou uma única instrução
{
    // região paralela: só uma thread cria a tarefa; outra thread pode executá-la
    printf("Arquivo: %s | Thread: %d\n", node->filename, omp_get_thread_num());
}

Cláusulas disponíveis

CláusulaEfeito
shared(list) Variáveis na list são compartilhadas entre todas as tarefas e a thread que as criou.
private(list) Cada tarefa obtém uma cópia não inicializada da variável. O valor original não é visível dentro da tarefa.
firstprivate(list) Como private, mas cada cópia é inicializada com o valor da variável no momento da criação da tarefa.
final(expression) Se expression for verdadeira, todas as tarefas internas são geradas como included (executadas inline pela thread atual).
depend(dependence-type: list) Especifica dependências entre tarefas (tipo in, out, inout) para ordenação.
priority(value) Define a prioridade de agendamento da tarefa. Valores maiores têm preferência.

Ciclo de vida de uma tarefa

  1. Criação (encoding): A thread que encontra o task empacota o contexto (valores das variáveis no momento) em um descriptor e o entrega ao task runtime.
  2. Agendamento (scheduling): O runtime atribui a tarefa a uma thread do time. Uma thread pode criar tarefas e outra executá-las.
  3. Execução (execution): A thread designada executa o corpo da tarefa.
  4. Junção (join): O taskwait aguarda a conclusão de todas as tarefas pendentes geradas pela região atual.
Ponto crucial: A thread que cria a tarefa (task) pode ser diferente da thread que a executa. Isso é o inverso do parallel for, onde a thread que itera é a que executa.

3. O problema central: cada nó é processado quantas vezes?

O comportamento do processamento de lista com tarefas depende de como o laço de travessia é escrito. Existem três padrões principais:

Padrão A — Laço dentro da região paralela (INCORRETO)

#pragma omp parallel
{
    // PROBLEMA: todas as threads executam o laço completo
    Node *current = head;
    while (current != NULL) {
        #pragma omp task
        {
            printf("%s\n", current->filename);
        }
        current = current->next;
    }
}
  • Todas as threads entram na região paralela.
  • Cada thread percorre a lista inteira.
  • Cada nó é processado por tantas vezes quantas forem as threads do time.
  • Resultado: $N$ nós × $T$ threads execuções.

Padrão B — Laço fora da região paralela, single no laço (CORRETO)

#pragma omp parallel
{
    #pragma omp single
    {
        Node *current = head;
        while (current != NULL) {
            #pragma omp task
            {
                printf("%s | thread %d\n",
                       current->filename, omp_get_thread_num());
            }
            current = current->next;
        }
    }
    #pragma omp taskwait
}
  • Apenas uma thread executa o laço de travessia.
  • Essa thread cria uma tarefa por nó.
  • O runtime distribui as tarefas entre as threads do time.
  • O taskwait garante que todas as tarefas terminem antes das threads saírem da região.

Padrão C — Travessia sequencial antes da região paralela (alternativa)

// Primeira percorrida: contar nós (sequencial)
int node_count = 0;
Node *count = head;
while (count) { node_count++; count = count->next; }

// Alocar vetor de ponteiros (paralelo, task-based)
Node **nodes = (Node **)malloc(node_count * sizeof(Node *));
Node *fill = head;
for (int i = 0; i < node_count; i++) {
    nodes[i] = fill;
    fill = fill->next;
}

#pragma omp parallel for
for (int i = 0; i < node_count; i++) {
    process_node(nodes[i]);
}
  • Converte a lista em vetor primeiro; depois usa parallel for — evita o problema inteiramente.
  • Custo: $O(N)$ adicional sequencial para contar e copiar ponteiros.

4. Por que o comportamento varia entre execuções?

O task runtime do OpenMP é não-determinístico por design. O agendador pode escolher qualquer thread disponível para cada tarefa. Isso significa:

  • A ordem em que as tarefas são executadas varia entre execuções.
  • Se cada tarefa escrever em um acumulador compartilhado (por exemplo, count++), o valor final depende da ordem de interleaving — race condition.
  • Se cada tarefa escrever em uma posição distinta do vetor (por exemplo, results[i] = ...), não há race condition, mas a ordem de preenchimento é arbitrária.
Race condition vs. resultado variável: Quando cada nó é processado exatamente uma vez, mas a ordem varia, o resultado final pode ser diferente entre execuções se as tarefas escreverem na mesma variável compartilhada. Esse é o padrão da Tarefa 06 (Monte Carlo).

5. taskwait: aguardando todas as tarefas

O taskwait é uma barreira implícita para todas as tarefas geradas no bloco de código que o contém. Sem ele, as threads podem sair da região paralela antes que as tarefas terminem. 

#pragma omp parallel
{
    #pragma omp single
    {
        while (current != NULL) {
            #pragma omp task shared(current)
            {
                process_node(current);
            }
            current = current->next;
        }
    }
    // taskwait aqui: aguarda todas as tarefas criadas no single acima
    #pragma omp taskwait

    // Aqui, todas as tarefas já terminaram
    printf("Fim do processamento.\n");
}

Variantes de sincronização

DiretivaEfeito
taskwait Aguarda todas as tarefas filhas diretas do contexto atual.
taskgroup + taskwait Aguarda todas as tarefas de um grupo inteiro, incluindo tarefas aninhadas.
taskyield cede a thread corrente para que o scheduler possa executar outra tarefa pronta.

6. single: uma única thread no bloco

A diretiva #pragma omp single faz com que exatamente uma thread execute o bloco. As outras threads do time esperam no fim do bloco (barreira implícita), a menos que a cláusula nowait seja usada. 

#pragma omp single nowait
{
    // Apenas uma thread entra aqui; as outras passam direto
    Node *current = head;
    while (current != NULL) {
        #pragma omp task firstprivate(current)
        {
            printf("%s\n", current->filename);
        }
        current = current->next;
    }
}
// Se usasse nowait, as outras threads não esperariam o single terminar
// — perigoso se o código abaixo dependesse dos nós já estarem processados
firstprivate(current): Cada tarefa recebe sua própria cópia de current com o valor que current tinha quando a tarefa foi criada. Sem isso, todas as tarefas veriam o valor final de current após o laço terminar (provavelmente NULL).

7. omp_get_thread_num(): qual thread executa?

A função omp_get_thread_num() retorna o ID da thread que a chama, no intervalo [0, omp_get_num_threads() - 1]. 

int tid = omp_get_thread_num();    // ID da thread [0, T-1]
int nt  = omp_get_num_threads();   // total de threads no time

No Padrão B (correto), cada nó gera uma tarefa. Quando a thread 0 (ou qualquer thread designada pelo single) cria as tarefas, ela passa por cada nó e gera uma tarefa. As tarefas são então agendadas para as threads disponíveis — tipicamente de forma work-stealing: threads ociosas "roubam" tarefas de threads ocupadas.

Em uma execução típica com 4 threads, ao criar 10 tarefas, a thread 0 pode criar todas, mas as threads 1, 2 e 3 roubam tarefas para executar. A distribuição exata depende do scheduler e da carga de cada thread — e varia entre execuções.

8. Tabela de conceitos-chave

ConceitoDefinição
task Unidade de trabalho criada em tempo de execução por uma thread e potencialmente executada por outra.
taskwait Barreira que aguarda a conclusão de todas as tarefas filhas geradas no bloco atual.
single Diretiva que faz apenas uma thread do time executar o bloco; as demais esperam ao final (barreira implícita).
taskyield Diretiva que cede a thread atual ao scheduler para que outra tarefa pronta possa ser executada.
firstprivate Cada tarefa recebe uma cópia privada da variável, inicializada com o valor no momento da criação.
depend Cláusula que estabelece dependências (in/out/inout) entre tarefas para ordenação pelo scheduler.
Work-stealing Estratégia de agendamento onde threads ociosas roubam tarefas de threads ocupadas.
